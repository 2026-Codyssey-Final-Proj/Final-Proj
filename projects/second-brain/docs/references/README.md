# 참고 자료 — 무엇을 가져가나 (겹침 / 새로움)

<!-- claude-drafted: 2026-10-01 — 사용자 요청("하나하나 우리의 기준에 맞춰져 있는 내용이 겹치는것과 겹치지 않는것들로 2가지로 나누되 저장소 하나 하나 씩 가져갈것들을 나열해서 보여줘")으로 Claude가 8개 참고 자료 문서와 각 저장소 원문을 다시 읽고 썼다. 분류는 Claude의 판단이고, 가져갈지 확정은 사용자가 한다. -->

사용자가 만든 저장소 8개를 세컨드 브레인에 넣는 기준은 프로젝트 [CLAUDE.md](../../CLAUDE.md) "참고 자료 넣기"다.
이 문서는 각 저장소에서 가져갈 것을 **두 가지로 나눈다.**

- **겹침** — 이 워크스페이스의 기준(규칙·훅·게이트·세컨드 브레인 결정)에 **이미 같은 것이 있다.** 새로 만들 필요는
  없고, "예전에 스스로 이미 하던 것"이라는 확인이다. 오른쪽 칸이 우리 쪽 근거다.
- **새로움** — 우리 기준에 **아직 없다.** 가져가면 무언가가 새로 생긴다. 오른쪽 칸이 들어갈 단계다.

맨 아래 "제외"는 목적에 답하지 않거나 이미 다른 결정으로 빠진 것이다.

## 1. my-setup-proj — 이 작업의 초안

**겹침**

| 가져갈 것 | 우리 쪽 근거 |
|---|---|
| `feature/* → PR → 사용자 병합` (ADR-0023) | [git-workflow.md](../../../../.claude/rules/git-workflow.md) "병합은 사용자가 한다" |
| 계획에 없는 범위는 건드리지 않는다, 미리 만들지 않는다 | `karpathy-guidelines` 2·3번, `ponytail-review` |
| 결정마다 ADR을 남긴다(37건) | 3단계 [ADR 실무](../../../../docs/03-pattern-analysis/adr/README.md) |
| 로컬 우선(ADR-0015) | PRD 현재 상태 "데이터 저장은 일단 로컬" |
| 비밀값은 환경변수, OAuth 토큰 평문 금지 | [기록·보안 기준](../../../../.claude/rules/security-records.md) 2절 |
| 새 기능마다 "목적 중 어디에 답하나" 정합성 감사 | 방향 점검 페이지, "참고 자료 넣기"의 목적 연결 칸 |
| 사람 결정이 필요하면 멈춘다(`STOP_DECISION`), 커밋은 검증 뒤에만 | 세컨드 브레인 역할(코드는 Claude, 판정·병합은 사용자), `require-tests` 훅 |

**새로움**

| 가져갈 것 | 들어갈 단계 |
|---|---|
| **태그에 주인을 붙인다** — `source = user / agent`, Claude가 사용자 태그를 바꾸지 않는다(ADR-0029) | 2단계 요구사항 (태그를 Claude도 붙이게 되면) |
| **지식 추세 뷰** — 체크인 빈도·달성률·태그 분포로 "무엇을 배웠나"를 추세로(ADR-0036) | 3단계 시각화 설계 (P1 시각화의 측정 방법) |
| 체크인 7질문 중 **"상태"** 칸 — 나머지 6개는 qa-prep 6슬롯과 거의 같다 | 2단계 지식·할 일 항목 형식 |
| 레퍼런스 요약의 **추가·삭제 이력**(ADR-0037) | 3단계 저장 구조 (지금 `docs/references/`는 이력을 git에만 맡김) |
| **커밋 전 비밀값 검사 훅**(`check-secrets.sh`: 금지 경로 + 추가된 줄의 키 패턴, 탐지값 마스킹) | 워크스페이스 훅 — 기록·보안 기준이 "실제로 생기면 승격"이라 적어 둔 바로 그 장치 |
| **main에서 코드를 직접 고치려 하면 확인 요청** 훅(`hook-code-branch-guard.sh`) | 워크스페이스 훅 (지금은 규칙으로만 막음) |
| **수동 검증을 실제로 했다는 기록** — 자동 테스트만 통과하고 앱을 눈으로 본 기록이 없었다(D4) | 6단계 실측 |
| 정해진 시각에 돌리는 예약 실행(launchd, 매일 07:30) | 3단계 — "남은 날 알람"을 무엇으로 울릴지 후보 |
| 외부 API는 한 곳(에이전트)만 부른다(ADR-0006) | 3단계 — 외부로 나가는 경로를 한 곳으로 모으면 기록·보안 기준 3절 관리가 쉽다 |

## 2. LLM-Prompt-Engineering — ①~④ 가져가기로 확정

**겹침**

| 가져갈 것 | 우리 쪽 근거 |
|---|---|
| ② 원문에 없는 정보는 쓰지 않는다, 담당자를 추측하지 않는다 | [review-mode.md](../../../../.claude/rules/review-mode.md) 질문하는 법 6 "사용자가 한 말에서만 판단, 근거 없으면 공백" |
| ② 모르면 "확인이 필요합니다" | 같은 곳 6 (공백 표시), PRD 상태 태그 [미정] |
| ② 부족하면 확인 질문을 먼저(최대 3개) | 질문하는 법 1 "한 번에 최대 2개" — **숫자가 다르다(3 vs 2)**, 세컨드 브레인 요약 기능에서 어느 쪽을 쓸지 2단계에서 정할 것 |
| ④ 확정된 요구 유지, 바뀐 조건만 수정, 최신 정보 우선 | 확정 섹션 변경 기록, 재료 표 "지우지 않는다", 스냅숏 페이지 "원천이 맞다" |

**새로움**

| 가져갈 것 | 들어갈 단계 |
|---|---|
| ① **요약 출력 고정 형식** — 결정사항 / 할 일(업무·기한) / 리스크 / 후속 일정 / 확인 필요 사항 | 2단계 — "놓친 일" 한 단위 = 기한이 있는 할 일 한 줄 (담당은 항상 나) |
| ③ **환각 검증** — 같은 질문 → 원문 대조 → Pass(정답+근거, 또는 모른다+확인 제안) / Fail | 5~6단계 — Claude 요약 기능의 테스트 |
| ④ **10턴 문맥 유지 테스트**와 실패 사례 3개(담당자 지어냄, "간결하게"에 형식이 바뀜, 조건 변경 뒤 이전 요구 망각) | 5~6단계 테스트 |
| ④ 최종 출력 전에 이전 변경이 모두 반영됐는지 전체 검토 | 5단계 — 요약을 저장하기 전 마지막 확인 단계 |
| 비용 전략(출력 형식 지정, 긴 문서는 나눠서, 불필요한 요청 줄이기) | 2단계 비기능 요구 — 지금 비용 기준은 "유료 도구 안 씀" 하나뿐 |

## 4. No-Code-Workflow-Automation-Project

**겹침**

| 가져갈 것 | 우리 쪽 근거 |
|---|---|
| API 키는 환경변수, 저장소에 올리지 않는다 | 기록·보안 기준 2절 |
| 무료 플랜에서 되는 도구를 고른다 | "유료면 안 쓴다" (Motion·Kroki 판정) |
| Trigger → (Filter) → Action 으로 자동화를 쓴다 | 2단계 EARS — Event-driven("When …, the system shall …"), State-driven 문장과 같은 꼴 |
| 대량·복잡한 처리는 노코드보다 코드 | 세컨드 브레인은 Claude Code가 코드로 만든다 |

**새로움**

| 가져갈 것 | 들어갈 단계 |
|---|---|
| **실패 처리 3종** — 실패 알림 / 재시도 / 대체 경로(Fallback) | 3·5단계 — 자동화가 조용히 멈추면 그 자체가 "놓친 일" |
| **실행 로그** — 자동화가 언제 돌았고 성공했는지 | 5단계 — 진행 관리 페이지에 자동화 실행 기록 |
| **스크린샷·이메일·Webhook 주소 마스킹 확인** | 기록·보안 기준 — 지금은 코드·문서·커밋만 다루고 이미지(스크린샷)는 없다 |
| 외부 서비스로 나가는 자동화 경로를 하나씩 적기 | 2단계 보안 — 기록·보안 기준 3절 표에 행 추가 방식 |

**겹침**

| 실제 실행 화면을 캡처해 시나리오별로 문서화 | 6단계 — my-setup-proj D4(수동 검증 기록 없음)의 해법 |

| **일부가 실패해도 경고를 남기고 결과는 만든다**, 실패하면 1번 재시도 | 3·5단계 — No-Code의 실패 처리와 같은 재료 |

## 반복되는 새 재료 — 두 개 이상의 저장소에서

| 재료 | 나온 곳 | 왜 중요한가 |
|---|---|---|
| **자동화 실패 처리** (알림·재시도·대체 경로·부분 실패 경고) | No-Code, K-Travel, my-setup-proj(재기동 백오프) | 성공 기준이 "놓친 일의 수"인데, 자동화가 조용히 실패하면 놓친 일이 보이지 않게 생긴다 |
| **실제로 써 본 기록** (수동 검증·화면 캡처·AI 사용 로그의 검증 방법) | my-setup-proj(D4), seoul, data-ai-assistant | 자동 테스트만으로 "놓친 일이 줄었다"를 말할 수 없다 — 6단계 실측의 재료 |
| **요약의 형식과 검증** (고정 출력 형식, 관찰-해석-행동, 환각 검증) | LLM-Prompt-Engineering, seoul, data-ai-assistant | 세컨드 브레인의 핵심 동작이 "넣으면 Claude가 요약"이다 — 요약 품질이 곧 지식 창고의 품질 |
| **비용 상한** (출력 길이, 요청 줄이기, 싼 단계 먼저) | LLM-Prompt-Engineering, data-ai-assistant, AI-Brand | 지금 비용 기준은 "유료 도구 안 씀"뿐이다 |
| **비밀값·인증의 기계적 확인** (커밋 전 검사 훅, 배포 전 인증 확인, 스크린샷 마스킹) | my-setup-proj, data-ai-assistant, No-Code | 가장 큰 걱정이 계정 탈취다 — 지금은 읽고 따르는 기준뿐이다 |

## 제외 — 가져가지 않는 것

| 무엇 | 이유 |
|---|---|
| my-setup-proj의 Daily Brief, Gmail·Calendar 동기화, OKR 화면 | 생활 관련은 AI 운영체제로 분리. OKR은 성공 기준(놓친 일)과 다른 축이라 지금은 넣지 않음 |
| my-setup-proj의 Electron·위젯 셸·웹 데모 모드 | 화면·기기 방식은 3단계에서 폰 접근과 함께 정한다 — 미리 정하지 않음 |
| LLM-Prompt-Engineering의 모델 비교(GPT-5.5 선정) | 세컨드 브레인은 Claude를 쓴다 |
| AI-Brand의 영상·음악·음성 도구 | 유료이고 영상 제작은 목적 밖 (Motion 판정과 같음) |
| No-Code의 Make·Zapier 자체 | 회의록을 외부 서비스로 보낸다 — 개인정보 외부 전송 기준과 충돌 |
| data-ai-assistant의 Firestore·Render·Vercel 배포 구조 | 저장은 로컬 마크다운으로 정했다 |
