# 참고 자료 — 코딩마라톤 자료 16개에서 배울 것

- **무엇:** 사용자가 받은 코딩마라톤(강의) 자료. 분석설계 프롬프트 5종(유스케이스·프로세스·UI/UX·데이터베이스·아키텍처),
  API 서버 점검·개선 가이드, 공유 Ollama 서버 가이드, 이슈리포트 프롬프트와 그 결과물(마크다운·슬라이드),
  데이터 기반 비즈니스 모델(DDBM) 가이드라인 PDF와 캔버스 사진, 지식 관리 스킬 2개(pro-know·doc2know)와 계획 문서.
- **기준:** 우리 과정 = 7단계 워크플로우 + 세컨드 브레인(지금 2단계). "배울 것"만 적었다 — 강의 과제 자체를 하라는 뜻이 아니다.
- **이용 조건:** DDBM 가이드라인 PDF는 "복제 및 재활용 시 작성자와 상의"라고 적혀 있다 — **틀(블록 이름)만 생각의 도구로 쓰고
  본문은 옮기지 않는다.** 다른 자료도 원문 대신 원칙만 적었다. 자료에 나오는 강사·다른 수강생의 이름·경로는 적지 않았다.

**가져오는 순서 (사용자 결정 2026-10-02):** 1 유스케이스 → 2 근거·확실성 표시 → 3 DDBM 렌즈. 적용 결과는 세션 파일 2단계 절에 쌓는다
(1 → "2·3-b. 유스케이스" — 보류). **진행 방식(2026-10-03):** 한 파일씩 천천히 이해한 뒤 적용한다. **멈춤(2026-10-03):** 사용자 요청으로 2번(이슈리포트 프롬프트) 설명까지 하고 2단계 작업으로 돌아감 — 다시 열 때 2번의 선택(가장 와닿는 장치)부터.

## 1. 분석설계 프롬프트 — 유스케이스

- **확정한 EARS 요구를 유스케이스로 펼치면 빠진 흐름이 보인다.** 사전·사후조건, 기본흐름(액터 행위 | 시스템 행위 두 열을
  모두 채움 — 액터 칸이 비면 유스케이스를 잘못 고른 것), 대체흐름 A1…, 예외흐름 E1….
- **예외흐름은 유스케이스당 최소 1개, 원천의 위험·실패에서 끌어낸다.** 우리 S1~S8(Unwanted)이 곧 예외흐름의 원천이다.
- **한 번에 하나씩 쓴다** — "뒤쪽 유스케이스의 밀도가 반드시 떨어진다." 우리 질문 규칙 2번(한 메시지 최대 5개)과 같은 이유.
- 원천에 없는 값은 `자료 없음 — 확인 필요`, 설계 판단은 `[추론]` 표기 — 우리 질문 규칙 6번과 같다(겹침).

## 2. 이슈리포트 프롬프트 + 결과물(마크다운·슬라이드)

- **사실 문장에는 근거 번호, 해석에는 `[분석]` 머리표.** 근거 없는 문장은 반드시 해석으로 표시된다.
- **결론에 확실성 등급** — 높음(여러 원저가 일관), 중간(소수·간접), 낮음(단일 연구·의견).
- **"확인된 것 / 아직 확인되지 않은 것(왜 — 미측정·미공개·추적 부족)" 대조표.** 모르는 것을 숨기지 않고 이유와 함께 적는다.
- 두괄식, 뒤 절은 앞 절의 근거만 쓴다, **"하지 말아야 할 것"도 제언에 넣는다**, 한계와 원자료 대조가 필요한 항목을 지목한다.
- 슬라이드 결과물은 장마다 `[FACT]`·`[ANALYSIS]`·확실성 표시를 그대로 시각화했다 — 지식 시각화(F9)·발표 자료(F14)의 예.
  다만 **슬라이드가 그림으로만 되어 있어 글자를 찾거나 고칠 수 없다** — 지식 창고에는 원천 텍스트가 있어야 한다(반대 사례).
- → 세컨드 브레인의 지식 항목 **관찰 → 해석 → 행동(F10)**에 "근거"와 "확실성" 두 칸을 더할 후보.

## 3. DDBM(데이터 기반 비즈니스 모델) 가이드라인 + 캔버스 사진

- 11블록: 미션 · 핵심 활동 · 핵심 파트너 · **핵심 장벽** · 핵심 이네이블러 · **핵심 데이터** · 가치 제안 · **부정적 영향** · 혜택 · 비용 · 수익.
- 우리 PRD 11섹션에는 **부정적 영향**(예: 세컨드 브레인에 기대다 스스로 기억하지 않게 됨, 팀원 정보 저장의 위험)과
  **핵심 데이터**(이 시스템이 기대는 데이터가 무엇인가 — 마감, 할 일, 배운 것)를 따로 묻는 칸이 없다. 2단계 렌즈로 한 번 대 볼 만하다.
- 비용 블록은 Q7(비용 상한)과 이어진다. 수익 블록은 개인 사용이라 해당 없음.

## 4. 분석설계 프롬프트 — 프로세스

- **게이트 5속성: 위치 · 조건 · 미통과 시 결과 · 해제 주체 · 근거.** "해제 주체가 없으면 게이트가 아니라 벽이다."
  → 우리 워크스페이스 게이트(gates.md)도 Recycle일 때 **누가 무엇을 하면 풀리는지**를 적으면 같은 원칙이 된다.
- **분기 중 "처리 중단"으로 끝나는 것만 게이트로 올린다**(단순 대체 경로는 내부 분기). 경고로 약하게 만들지 않는다.
- 단계마다 **입력 · 처리 · 출력 · 근거** 표(IPO), 프로세스 사이 **인계물에 만료·무효 조건**, "어느 유스케이스도 빠지지 않았나" 표로 닫기.
- 도면: 정상 종료(stop)와 **차단 종료(kill)를 색으로 구분**, 도면 아래 "읽는 법" 문단.

## 5. 분석설계 프롬프트 — UI/UX

- **설계 원칙은 상상하지 않고 게이트·규칙에서 역산**하고, **"원칙이 배제한 흔한 선택"** 표를 붙인다 — 무엇을 안 하기로 했는지가 설계다.
- **화면을 저장 구조보다 먼저** 그린다 — 화면이 요구하는 값이 곧 저장할 칸이고, 안 쓰이는 칸이 드러난다.
- 표시 항목마다 **어디서 온 값인지(데이터 바인딩)**를 적는다.
- 게이트는 **버튼을 비활성화하고 이유를 붙인다**. 해제 주체가 내가 아니면 버튼은 "요청 보내기"다. 토스트·경고로 표현하지 않는다.
- **결측을 회색 placeholder로 두지 않는다 — "아직 안 채움"과 "채우면 안 됨"을 구분**한다. 우리 [초안]/[미정]/[확정] 표시와 같은 생각.
- 모든 화면 위에 **진행 레일**(지금 어디, 어디가 막혔나) — 우리 방향 점검 페이지의 "지금 사용자 차례"와 같은 역할.

## 6. 분석설계 프롬프트 — 데이터베이스

- 화면 표시 항목을 전부 모아 **저장 / 유도(계산 가능) / 상수**로 판정. **유도값은 저장하지 않고, 저장해야 하면 고정 근거를 적는다.**
- **같은 유도값을 두 곳에서 계산하지 않는다** — 언젠가 달라지고 어느 쪽이 맞는지 모른다. 우리 "상태의 원천은 게이트 로그 하나"와 같다.
  → 세컨드 브레인 예: "남은 날"은 마감에서 계산하는 값 — 파일에 적지 않는다.
- **규칙마다 어디서 강제되는지 명시**(제약·트리거·앱). "어디서 강제되는지 모르는 규칙이 가장 위험하다."
- **제약은 일부러 위반해 거부되는지 확인해야 끝난다** — 확인하지 않은 제약은 주석과 같다(API 가이드 D11, 우리 TDD와 같은 생각).
- 보존기간·임계값이 원천에 없으면 **지어내지 않고 미해결로** — 우리 Q 값들을 비워 둔 방식과 같다(겹침).

## 7. 분석설계 프롬프트 — 아키텍처

- 모듈 경계 3기준: **① 데이터 쓰기 주인은 한 모듈 ② 한 유스케이스는 한 모듈이 주도 ③ 게이트를 사이에 둔 두 행위는 다른 모듈.** 충돌하면 ①.
  my-setup-proj ADR-0011(쓰기 주체 분리)과 같은 교훈.
- **의존에 순환이 없어야 하고, 모두가 쓰는 모듈(근거·감사)은 아무도 부르지 않는 말단**이어야 한다.
- 도면은 관점별로 나누고 한 장에 요소 25개 이하, 도면마다 "읽는 법" — 우리 다이어그램 지침에 더할 후보.

## 8. doc2know 스킬 (지식베이스 변환)

- 지식 노트 머리말 필드 중 우리에게 새로운 것: **level(Seedling → Budding → Evergreen — 노트의 성숙도)**, type(개념·방법·아이디어 등),
  status(draft·review·published), parents/related/**antithetical(반대) 개념**, relationships(위키 링크는 이 칸에만).
  → "지식이 자란다"(P1)를 노트 단위로 잴 수 있는 칸 — Q4("스스로 발전"을 무엇으로 재나)의 후보.
- **합칠까 · 덧붙일까 · 새로 쓸까** 판단: 겹침이 크면 합치고, 중간이면 새 파일에 교차 링크, 적으면 새로. 지식 창고가 커질 때의 규칙 후보.
- **보안 주의 — 스크립트는 실행하지 않는다.** `generate_yaml.py`·`orchestrator.py`가 문서 내용을 **코드에 박힌 사설망 주소의 Ollama 서버**로
  보낸다(우리 서버가 아니다). 개인정보를 밖으로 보내는 도구는 들이지 않는다는 기준과 충돌 — **개념만 가져온다.**

## 9. pro-know 스킬 + "pro-know & doc2know 통합 계획" 문서

- 목표 문장: **"미래의 나(또는 팀원)가 다시 배우지 않고 이해하고 행동할 수 있는 문서."** — 이 워크스페이스의 원문제
  ("배운 게 다음 프로젝트에 재사용되지 않는다")와 같은 말이다.
- 최소 문서 5절: 개요 · 구현 내용 · **문제와 해결** · **결과와 지표** · 결론과 배운 점. → 7단계 회고·프로젝트 마무리 문서의 뼈대 후보.
- 계획 문서의 흐름: 원본에 **"정리 완료" 표시(`kb_status: classified`, 날짜, 옮겨 간 곳)**를 남겨 같은 것을 두 번 처리하지 않는다.
  → 세컨드 브레인 F1~F3(넣기 → 요약 → 저장)에서 "이미 처리한 입력" 표시 후보.
- 스크립트(`gather_related_docs.py` 등)는 로컬 파일만 읽는다 — 그래도 외부 스킬이므로 들일 때는 명령 4(외부 통합 분석)를 거친다.

## 10. API 서버 점검 가이드

- **네 축의 순서에 이유가 있다:** 연결 → 계약 → 성능 → 실패설계. 앞이 안 되면 뒤를 잴 수 없다.
- **"합격선은 전항 통과가 아니라 전항 기록 — 빈칸만이 미제출."** 우리 6단계 DoD("미달이어도 기록")와 같다(겹침). 결과 칸에는 "OK"가 아니라 실제 값.
- **점검 중에는 고치지 않는다** — 고치면 무엇을 재고 있었는지 사라진다. 경로를 가정하지 않고 먼저 찾는다.
- 보안 항목 중 우리 기준에 없는 것: **비밀값을 명령행 인자로 넘기지 않는다**(다른 사용자의 `ps`에 보인다), **비밀값을 확인할 때도
  화면에 찍지 않고 있음/없음 또는 sha256 앞 8자 지문만**, **로그에 입력 원문을 남기지 않는다**("이 줄이 6개월 뒤 누군가의 화면에
  떠도 괜찮은가"), 서버는 `127.0.0.1`에만, **모르는 필드는 거절**, **상한 초과는 잘라서 받지 말고 거절**.
  → 기록·보안 기준 6-3과 비밀값 검사 훅을 만들 때 그대로 쓸 재료.

## 11. API 서버 개선 가이드

- **"바꾸지 않아도 되는 것"을 먼저 적는다** — 고칠 것은 고장 · 노출 · 미검증 셋뿐. karpathy-guidelines 3번(필요한 곳만)과 같은 생각.
- 한 번에 하나만, **같은 자로 전·후 두 숫자**, 계약과 설정을 함께, 고치기 전 사본.
- **"행선지 없는 보류는 결국 무시된다."** 보류는 큐에 쌓고 **누가 언제 보는지** 한 줄을 적어야 끝난다.
  → 우리 S1b "확인 필요" 표시의 행선지 = **일요일 놓친 일 점검(Q1)** 때 함께 본다는 식으로 이을 후보.
- 낮은 확신도는 오류(500)가 아니라 정상 응답 + "보류" — 요약을 확신하지 못할 때의 처리와 같은 구조.

## 12. 공유 Ollama 서버 가이드

- **재시도는 연결 오류·시간 초과에만, 4xx는 즉시 실패** — 우리 S2b(재시도 상한)를 정할 때 "무엇을 재시도하나"의 기준. 간격 3초·6초.
- 공유 자원 규칙(동시 1건, 출력 길이 상한, 결과 캐시, 폴링 금지) — Q7(비용 상한)과 같은 생각.
- **로컬 모델이라는 선택지:** 요약·임베딩을 컴퓨터 안의 모델로 돌리면 내용이 밖으로 나가지 않는다. 3단계에서 "Claude 대신·함께
  로컬 모델"을 비교할 재료. 다만 이 가이드의 서버는 **수업용 공유 서버**라서 세컨드 브레인의 개인 데이터를 보내면 안 된다(S4).
