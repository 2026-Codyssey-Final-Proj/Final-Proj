# 요구사항 접수 — 유지보수 중 새 요구가 오면 어디를 고칠지 정하는 절차 (초안)

<!-- claude-drafted: 2026-10-14 — 사용자 요청("요구사항들을 넣으면 너가 확인해서 어디에 업데이트를 진행하면 좋을지 준비")으로 Claude가 쓴 초안이다. 확정은 사용자가 한다. -->

7단계(유지보수) 이후 사용자가 새 요구를 말하면, **Claude가 분류하고 "어디를 어떤 순서로 고칠지"를 한 장으로 만든다.** 고치는 일은 사용자가 "예" 한 뒤에 한다.
이 절차의 목적은 요구가 왔을 때 문서·코드·시험·팀 저장소 중 **빠뜨리거나 어긋나는 곳이 없게** 하는 것이다(상태가 여러 곳에 흩어져 어긋난 전례).

## 1. 접수 한 장 (Claude가 만든다)

| 칸 | 내용 |
|---|---|
| 요구 원문 | 사용자가 한 말 그대로. 먼저 원문 표(세션 파일 "대화에서 나온 재료")에 날짜와 함께 적는다 |
| 종류 | 아래 2절의 번호 하나(둘 이상이면 나눠서 따로 접수) |
| 이미 있나 | 겹치는 EARS·ADR·시험이 있는지(있으면 "새 요구가 아니라 변경") |
| 충돌 | 확정된 값(Q·ADR)과 부딪히는 곳 |
| 고칠 곳 | 아래 3절 순서대로, 파일 이름까지 |
| 사용자가 정할 것 | 한 번에 최대 5개, 다른 결정을 좌우하는 것은 단독으로 |
| 하지 않을 것 | 이번 변경이 건드리지 않는 곳(범위를 좁힌다) |

## 2. 요구 종류와 먼저 정할 것

| # | 종류 | 먼저 확인할 질문 | 고칠 곳(원천 → 파생) |
|---|---|---|---|
| 1 | 새 기능(EARS 일반·사건·상태) | 어느 UC·목적(P1~P8)에 닿나, 문장당 동작 하나인가 | 세션 파일 EARS 절 → 우선순위·추적표 → `05-implementation` 대응표 → 시험 → 코드 |
| 2 | 실패·보안(Unwanted) | 어떤 위반 시도인가, Top 10 묶음 어디인가 | 세션 파일 EARS Unwanted + 보안 묶음 → 대응표 → **위반 시도 시험 먼저** → 코드 |
| 3 | 숫자 기준 바꿈(Q) | 무엇을 재고 어떻게 재나(Scale·Meter), 이미 잰 값이 있나 | 세션 파일 정량화 → 설정값 표 → 측정 문서(`06-service`) → 코드의 상수와 시험 |
| 4 | 구조·저장 결정이 바뀜 | 이전 결정 ADR이 무엇인가 | **새 ADR**(Accepted 본문은 고치지 않고 `Superseded by`만) → 설정값 표 → 영향받는 코드 |
| 5 | 생활 관련(일정 정리·카톡·공지·메일) | 세컨드 브레인 핵심(지식·진행·놓친 일)인가 | 핵심이 아니면 `projects/ai-os` 재료 표(원문 사본), 이 프로젝트 문서는 고치지 않음 |
| 6 | 보이는 화면·시각화 | 어떤 정보를 누가 어디서 보나 | 화면 fixture 문서 → (구현은 7단계 이후) |
| 7 | 데이터 정리(책·README·버전) | 어느 책에 닿나 | `07-maintenance/library-catalog-design.md`의 L1~L6 |
| 8 | 규칙·훅·작업 방식 | 한 프로젝트만인가 모두인가 | 루트 `consistency.md` 지도 → 규칙·훅 → CLAUDE.md |
| 9 | 버그·문구 | 요구가 아니라 결함인가 | 시험을 먼저 추가 → 코드. 문서는 건드리지 않음 |

## 3. 고치는 공통 순서

1. **원천:** 요구 원문 표 → 세션 파일(EARS·Q) 또는 ADR. 사용자 확정 표시(`[확정 날짜]`)를 붙인다.
2. **파생:** 대응표(`tasks-and-traceability.md`), 측정·계획 문서, PRD 변경 기록(확정 섹션을 고쳤다면).
3. **코드·시험:** TDD — 시험을 먼저 쓰고 빨간불을 확인. 세컨드 브레인 코드는 Claude가 쓴다.
4. **데이터:** 개인 데이터 폴더를 건드린다면 `data` 브랜치, 비밀값 검사를 통과한 뒤.
5. **팀 저장소:** 같은 변경을 개인 정보 없이 옮긴다(`PROGRESS.md`가 게이트 로그 사본).
6. **기록:** 게이트 로그에 한 줄, 7단계 이후라면 회고 입력.

PR은 만든 뒤 같은 브랜치에 더 올리지 않는다. 병합은 사용자가 한다.

## 4. 이 절차가 하지 않는 것

- 사용자가 확정하기 전에 문서를 고치지 않는다. 접수 한 장까지가 Claude의 일이다.
- 확정된 요구를 조용히 바꾸지 않는다. 바꾸면 이전 값을 변경 기록에 남긴다.
- 요구가 지식(P1)과 놓친 일(Q1) 어느 쪽 성공 기준에 닿는지 분명하지 않으면 **한 번 묻는다**(두 기준은 다른 축이다).

## 5. 예 (모양을 보이기 위한 가짜 요구)

| 칸 | 예 |
|---|---|
| 요구 원문 | "점검 보고에 지난 3주 추세 한 줄을 넣고 싶다" |
| 종류 | 1 새 기능 (Q1·Q4 표시) |
| 이미 있나 | 점검 보고에 주별 값은 있고 추세 줄은 없음 |
| 충돌 | 없음 (보고에는 이름·개수만, S4 유지) |
| 고칠 곳 | ① EARS 새 문장 ② 추적표·대응표 ③ `check_report.py` 시험 → 코드 ④ 팀 저장소 |
| 사용자가 정할 것 | 추세를 몇 주로 볼지, 표현(숫자/화살표) |
