# 5→6 게이트에서 받을 질문과 답 (초안)

<!-- claude-drafted: 2026-10-13 — 사용자 요청("이것들에 대한 답 초안 작성", "문서로 저장해줘")으로 Claude가 대응표·결정 기록·시험을 근거로 초안을 썼다. 답의 이유가 사용자에게 있는 곳은 [사용자]로 비워 뒀다. 확정과 게이트 판정은 사용자가 한다. -->

[리뷰 렌즈](../../../../.claude/rules/review-mode.md)의 "청중이 물을 질문"에서 5→6 게이트에 맞춰 Claude가 만든 질문 세 개와, 지금 있는 근거로 쓴 답이다.
답은 Point(결론) → Reason(이유) → Example(근거) → 약한 고리(솔직히) 순서다. 근거는 [대응표](tasks-and-traceability.md)와 코드·시험이다.
재료가 없는 곳은 지어내지 않고 **[사용자]** 로 남겼다 — 공백이 가장 중요한 부분이다.

## 이 프로젝트의 구조를 읽는 법 (사용자 2026-10-13)

> "현재 구조는 내가 테스트하며 문제를 알도록 하는 것이고, 팀으로 진행하는 것은 우리의 프로젝트를 개인이 사용한다면 이걸 가져가서 사용할 것이다라고 하는 것이야"

| | 지금 (V1 개인 워크스페이스) | 팀 프로젝트로서 |
|---|---|---|
| 무엇인가 | 사용자가 **자기 데이터로 직접 써 보며 문제를 찾는** 시험 환경 | 개인이 **이 프로젝트를 가져가서 자기 것으로 쓰는** 형태 |
| 데이터 | 사용자의 `data` 폴더 | 각 사용자의 것. 팀 저장소에 두지 않음 |
| 그래서 | 개인 정보·개인 연결이 섞여 있어도 시험이 목적 | 팀 저장소에는 코드·규칙·공유본만 있고, 개인 정보는 처음부터 없음 |

아래 답 3번은 이 읽기를 전제로 한다.

## 1. S3·S1a는 코드로 증명이 안 되는데 왜 통과로 보나요?

**Point.** 코드가 증명하는 것과 사람이 확인하는 것을 나눠서 적었고, 사람이 확인하는 부분은 **저장 전에 사용자가 직접 보고 "예"를 하는 단계**로 막았다. "증명됨"이 아니라 "통제됨"으로 통과로 본다.

**Reason.**
- S1a(원문에 없는 정보)는 **부분적으로 코드가 본다.** 날짜·숫자·주소가 원문에 있는지 검사하고(`summary_rules.ungrounded`), 위반 시도 시험이 7개 있다. 이름·사실 관계는 못 본다.
- S3(팀원은 이름·직책·한 줄)는 이름을 정확히 찾는 코드가 없다. 이름 탐지는 단어 목록 수준이라 놓치는 것이 많고, 팀 보안 문서도 같은 이유로 "막지 않고 알리고 사람이 고르게" 한다(보안 기준 6-3과 같은 원칙).

**Example(근거).**
- 지식·점검·일정은 쓰기 전에 항상 "이렇게 정리할게요" 한 장을 보여 주고 승인을 받았다(실사용 3건: 지식 저장, 점검 보고, 이번 주 계획).
- 저장된 문서 6개에는 다른 사람의 정보가 없다(2026-10-13 기준).
- 코드로 못 미치는 부분은 대응표에 "절차"·"부분"으로 명시했고 숨기지 않았다.

**약한 고리.** 사용자가 승인 단계에서 못 보면 S3는 뚫린다. 지금은 Claude가 거르는 약속에 의존한다. 이 위험은 사람이 보는 한 건씩의 승인으로만 낮아진다.

**사용자 결정 (2026-10-14):** 인정("2~5 전부 예"). **[사용자]** 인정하는 이유는 아직 사용자의 말로 적히지 않았다 — 위 Reason은 Claude가 기록에서 쓴 것이다.

## 2. Q11·Q12·60분 같은 잠정값으로 6단계 실측이 의미가 있나요?

**Point.** 의미가 있다. 6단계 게이트가 요구하는 실측의 대상은 잠정값이 아니라 **핵심 목표(Q1~Q4)** 이고, 잠정값(Q11·Q12·할 일당 시간)은 6단계에서 **바꾸기 위해 재는 값**이다.

**Reason.**
- 6단계 완료 기준은 "2단계 Planguage Goal을 실측해서 달성 여부가 기록됨"이다. 대상은 Q1(놓친 일 주 1개 이하), Q2(알람 도착), Q3(찾기 10초·2번), Q4(남기기 주 3개 등)이며 이 값들은 잠정이 아니다.
- Q11(하루 3시간)·Q12(주 10개)는 F17(이번 주 일정 제안, Should·매력)의 상한이고, 사용자가 "지금의 내용은 테스트로 변경될 사안임"이라고 직접 말했다. 이 값이 바뀌어도 Goal 실측은 흔들리지 않는다.

**할 일당 시간 — 사용자 결정 (2026-10-13):**

> "기본값은 1시간 이지만 검색한 결과 평균치에서 사람들에게 여유로운 시간들로 선택지를 주고 시간을 정하도록 할것"

| 칸 | 내용 |
|---|---|
| 기본값 | 1시간(60분) 유지 |
| 정하는 방식 | 사용자에게 **여유로운 시간 선택지**를 주고 사용자가 시간을 고른다 |
| 선택지의 근거 | 아래 "선택지 초안" — 검색으로 찾은 자료를 근거로 Claude가 만든 안. **"평균치"라고 할 만한 믿을 만한 단일 수치는 찾지 못했다** |
| 구현 상태 | **구현함(2026-10-13).** 할 일 문서에 `예상 시간`(30분 단위)을 적고, `plan_week`가 할 일마다 그 값을 쓴다. 완료하면 `실제 시간`을 기록하고, 다음에 같은 목적의 일을 넣을 때 그 기록으로 묻는다 — [ADR-0009](../03-pattern-analysis/adr/0009-task-time-data.md) (`main`에 병합됨, PR #90) |

### 할 일당 시간 선택지 초안 (2026-10-13, Claude가 자료를 찾아 만듦 — 확정은 사용자)

| 선택지 | 구성 (25분 집중 + 5분 쉼을 한 칸으로) | 근거 |
|---|---|---|
| 30분 | 1칸 | 25분 집중 단위 |
| **1시간 (기본)** | 2칸 | 사용자가 정한 기본값 |
| 1시간 30분 | 3칸 | 여유를 한 칸 더 — 아래 "여유를 두는 이유" |
| 2시간 | 4칸 | Pomodoro 창안자가 말한 "2시간 공부 단위"가 4칸이고, 시험 준비에서 사용자가 쓴 값과 같음 |
| 3시간 | 6칸 | 하루 상한(Q11 = 3시간)을 **전부** 쓴다 — 선택할 때 "오늘 상한을 모두 씀"을 표시 |
| 직접 입력 | — | 위 값에 맞지 않을 때 |

**여유를 두는 이유 (자료가 말하는 것).**
- 사람은 **자기 일의 시간을 짧게 잡는 경향**이 있다(계획 오류, Buehler·Griffin·Ross 1994). 졸업논문을 쓰는 학생 33명의 "가장 가능성 높은" 예상은 평균 33.9일이었는데 실제는 55.5일이었고, 예상한 날짜에 끝낸 사람은 29.7%였다. "모든 게 잘 풀리면"의 예상은 21.4일, "모든 게 최악이면"의 예상도 48.6일로 실제(55.5일)보다 짧았다. 수업 과제를 대상으로 한 설문에서도 학생들은 이전 과제의 약 68%를 예상보다 늦게 끝냈다고 답했다.
- **이 숫자를 한 시간짜리 일에 그대로 쓰지 않는다.** 위 연구는 몇 주짜리 과제이고, 짧은 일에서는 효과가 일정하지 않다는 보고도 있다. 쓰는 것은 방향(짧게 잡기 쉽다)뿐이다.
- 같은 연구의 4번째 실험에서, **비슷한 일에 실제로 걸린 과거 경험을 떠올리며 예상하게 하자 낙관 편향이 사라졌다.** 그래서 선택 화면에 "비슷한 일에 실제로 걸린 시간"을 보여 주는 쪽이 인터넷의 평균치보다 낫다. 이를 위해서는 완료할 때 "실제로 얼마나 걸렸어요?"를 한 번 묻고 기록해야 한다(지금은 그 기록이 없다 — 제안).

**25분 단위를 쓴 이유와 한계.**
- 25분 집중 + 5분 쉼은 Pomodoro 기법의 단위이고 창안자의 개인 경험에서 나왔다. 연구가 정한 최적값이 아니다.
- 2025년 대학생 94명 연구(검색 결과 요약으로만 확인, 프리프린트 원문은 열리지 않아 **직접 확인하지 못했다**)는 구조화된 휴식이 피로·집중에는 도움이 되었으나 해낸 작업량의 차이는 없었다고 보고했다. 25분과 50분 중 무엇이 낫다는 근거는 찾지 못했다.
- "집중은 15분 후 떨어진다", "90분이 최적"이라는 주장은 출처 없는 블로그 글뿐이었고 **근거로 쓰지 않았다.**

**찾은 자료 (확인 수준 표시)**

| 자료 | 확인 수준 |
|---|---|
| Buehler, R., Griffin, D., & Ross, M. (1994). Exploring the "planning fallacy". *Journal of Personality and Social Psychology, 67*(3), 366–381. [원문 PDF](https://bear.warrington.ufl.edu/brenner/mar7588/Papers/buehler-et-al-1994.pdf) | **원문에서 숫자를 직접 확인함** |
| [Pomodoro Technique — Wikipedia](https://en.wikipedia.org/wiki/Pomodoro_Technique) | 2차 자료(창안자의 25분 + 5분, 4칸 = 2시간) |
| [2025 프리프린트(대학생 94명, Pomodoro 대 자율 휴식)](https://www.preprints.org/manuscript/202503.0845/v1) | **열리지 않아 확인 못 함** — 검색 결과 요약만 봄 |

**사용자 결정 (2026-10-13):** "30분 단위로 작업을 작성이 가능하도록 하고 완료하면 어느정도 걸리는지에 대한 데이터를 수집 해서 다음번에 데이터를 기반으로 질문" — 위 값은 30분 단위로 적게 하고, 완료할 때 실제 시간을 모아 다음 질문의 근거로 쓴다(구현됨).

**사용자 결정 (2026-10-13):** "시간 선택지는 그대로 두고 병합했어" — 선택지 30·60·90·120·180분(3시간 포함)을 그대로 쓴다. 3시간은 하루 상한(Q11)을 전부 쓰므로 선택할 때 "오늘 상한을 모두 씀"을 표시한다.

**Example(근거).** F17·F18a를 실제로 2번 돌렸고 작업 시간 일정 2개를 만들었다(겹침 없음). 시험 준비 때는 사용자가 "총 2시간"을 알려 줘서 기본값 60분을 덮어썼다 — 할 일마다 시간이 달라서 하나의 기본값으로는 맞지 않는다는 첫 증거다.

**약한 고리.** 열린 할 일이 2~3개뿐이라 상한(3시간·10개)에 닿은 적이 없다. 지금 데이터로는 "상한이 맞는지"를 잴 수 없고, 6단계에서 할 일을 더 쌓아야 한다.

**잠정값을 바꾸는 기준(제안, 사용자가 고른다).** 6단계에서 이렇게 재고 Q11 칸에 날짜·이유와 함께 바꾼다: 제안 중 수정 없이 올린 비율, 올린 작업 시간 일정이 실제로 완료된 비율.

**[사용자]** 선택지 값과 근거 검색 결과(위 표).

## 3. 팀 저장소에서는 개인 데이터 없이 이 시스템이 어떻게 쓰이나요?

**Point.** 팀 저장소는 데이터를 모아 두는 곳이 아니라 **사용자가 가져가서 자기 데이터로 쓰는 프로젝트**다. 개인 데이터는 처음부터 팀 저장소에 두지 않고, 시연은 가상 데이터로 한다.

**Reason.**
- 위 "구조를 읽는 법"대로 지금 구조는 사용자가 직접 써 보며 문제를 찾는 시험 환경이고, 팀 프로젝트로서의 사용은 "개인이 이 프로젝트를 가져가 자기 것으로 쓴다"이다.
- 팀 문서의 공유 조건 1번이 "저장은 사람마다 따로, 팀과는 공유본만"이다. 팀 저장소에는 `data` 브랜치·할 일 문서·점검 보고 원문을 옮기지 않았다.
- 코드는 데이터 폴더 경로를 **인자로 받는다**(`briefing`·`check_report`·`planning`·`knowledge_list`). 폴더가 없으면 "찾지 못했습니다"라고만 말하고 "일이 없다"고 하지 않는다.

**Example(근거).** 팀 저장소에서 전체 테스트 13/13이 개인 데이터 없이 통과한다(시험의 실제 과목명은 가상 값으로 바꿔 올렸다). 팀 README의 흐름도 "대회 시연은 서버 없이 가상 데이터"이다. `share-prototype`은 "나만 / 요약만 / 팀 전체" 규칙을 가상 데이터로 시험했다.

**약한 고리.**
- **개인 데이터의 저장 구조는 아직 정해지지 않았다**(`PROGRESS.md` "남은 일" 1). 추천은 "로컬 파일부터, 백업이 필요하면 개인 저장소"다.
- 목적 5개(생활·학교·작업·대회·기타)와 번호 범위가 코드에 고정돼 있어, 가져가는 사람이 다른 분류를 쓰려면 설정값으로 바꿔야 한다.
- "가져가서 쓴다"를 시험한 적은 없다 — 사용자 본인 외에는 이 시스템을 써 본 사람이 없다.

**[사용자]** 대회 시연에서 개인 데이터를 어디까지 보일지(전부 가상 / 일부 실제).

## 정리

| 질문 | 답의 강도 | 막히는 곳 |
|---|---|---|
| 1. S3·S1a | 중 — 절차 의존을 인정해야 함 | 사용자의 인정 이유 한 줄 |
| 2. 잠정값 | 중상 — 실측 대상이 다름을 설명할 수 있음, 데이터가 얇음 | 선택지 값과 검색 근거, 선택지 구현 |
| 3. 팀 사용 | 중 — 구조는 있고 저장 선택이 미정 | 저장 구조, 시연 데이터 범위 |
