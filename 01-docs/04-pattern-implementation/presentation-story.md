## 1. 한 문장

**AI가 코드를 대신 써 주는 시대에, Floe는 "끝까지 만들고, 이해하고, 배움이 쌓이게" 길을 안내한다 — 결과를 대신 만들지 않고 사람이 스스로 결정하게 한다.** ([기획안](../00-overview/final-project-plan.md) "목표"에서 줄였다.)

발표 내내 이 한 문장으로 돌아온다. 슬라이드마다 "이게 그 문장의 어느 부분인가"가 보여야 한다.

## 2. 평가 배점과 슬라이드의 대응

배점은 [schedule.md](../00-overview/schedule.md) 1절 "평가 배점"이 원천이다. 발표(10점)는 **전달력 점수**이고, 나머지 90점의 근거를 10분 안에 보여 주는 자리이기도 하다.

| 영역 | 배점 | 발표에서 보일 것 | 슬라이드 |
|---|---|---|---|
| 기획 — 문제 정의 | 10 | 인터뷰에서 들은 말, 누가 겪는 문제인지 | 2 · 3 |
| 기획 — AI 적용의 합리성 | **20** | 코드 규칙이 판정하고 Claude는 초안 · 설명을 맡는 분업, "API 그대로가 아님" | 5 · 6 · 7 |
| 기술 — 구현 · 구조 | 20 | 아키텍처 · 데이터 파이프라인 그림, 구동 영상 | 5 · 7 |
| 실용 가능성 | 10 | 누가 어떻게 쓰나, 대회 이후 | 3 · 10 |
| 팀 · 협업 | **30** | 역할 분담과 균형, Git · Issue · 리뷰 증빙 | 9 |
| 발표 · 전달력 | 10 | 10분 안에 끝나는 논리 | 전체 |

기획 30 + 협업 30이 60%다. **협업 증빙은 "서면으로 보여야" 한다** — 슬라이드 9는 말이 아니라 화면(로그 · 이슈 · PR)을 보인다.

## 4. 슬라이드별 구성안

각 칸의 "채울 것"은 아직 근거가 없는 자리다.

### 슬라이드 1 — 표지 + 한 문장

| 칸 | 내용 |
|---|---|
| 보일 것 | 제품 이름 **Floe**, 마스코트 플로로, 1절의 한 문장 |
| 말할 것 | "AI가 코드를 써 주는 시대, 그래서 오히려 끝까지 이해하며 만드는 게 어려워졌습니다." (한 문장 안에 문제를 넣는다) |
| 근거 | [기획안](../00-overview/final-project-plan.md) |

### 슬라이드 2 — 문제

| 칸 | 내용 |
|---|---|
| 보일 것 | 인터뷰에서 들은 말 한두 줄 (**응답자 A** — 이름 · 소속 · 기수 없이) + 멈추는 순간 한 장면 |
| 말할 것 | 바이브 코딩은 쉬워졌는데, "지금 어디까지 왔고 다음에 뭘 하지?"에서 멈추고, 끝까지 만들어도 내 코드를 설명하지 못한다 |
| 채울 것 | `[ ]` 인터뷰 요약(#11)에서 고른 말. **인터뷰 전에는 기획안의 가설로만 말하고 "가설"이라고 한다** |
| 근거 | 기획안 "문제" · [인터뷰 질문지](../interviews/questionnaire.md) |
| 평가 칸 | 기획 · 문제 정의 10 |

| 칸 | 내용 |
|---|---|

| 말할 것 | 쉬운 말로 설계했다 — 화면 큰 글에는 전문 용어를 쓰지 않고, 나오면 그 자리에서 풀어 준다 (FR-13) |

| 평가 칸 | 실용 가능성 · 문제 정의 |

### 슬라이드 4 — 해결 한 장

| 칸 | 내용 |
|---|---|
| 보일 것 | 퀘스트 한 바퀴 그림: **생각 → 행동 → 기록 → 저장 → 버전**, 단계 끝에 **게이트**("이해하셨나요?" 예 / 아니요) — [requirements.md](../00-overview/requirements.md) 1절의 흐름도를 그대로 쓴다 |

| 지킬 것 | 5칸의 "저장 · 버전"(C-25)은 **아직 안 만든 부분이 있다** — 만든 만큼만 말한다. 화면 가능 범위는 임유정 · 이재엽에게 확인 |

한 문장(1절)을 한 번 더 말하고 질의응답으로 넘긴다. 질의응답 담당은 질문 유형별이다(기술 → 이재엽 · 임유정, 사용자 · UX → 고한결, 검증 → 두승현) — 누가 답할지 발표 전에 정해 두고, 질문이 오면 그 사람에게 넘긴다.

## 5. 자료 디자인 원칙

새로 정한 것이 아니라 이미 팀이 정한 것을 슬라이드에 옮긴 것이다.

| 원칙 | 내용 | 출처 |
|---|---|---|
| 색 | 얼음 파랑 테마. 유리 효과는 마스코트 카드에만, **글자 뒤는 불투명 면** | [화면 흐름](screen-flow-wireframe.md) 1절 |
| 마스코트 | 플로로는 **그림 코드(`seal.js`) 물범만** 쓴다. 이미지 파일(`mascot-v1.webp`)은 이용 조건을 확인하기 전까지 쓰지 않는다 | [3분 시연 스토리](demo-story-3min.md) 3절 |
| 쉬운 말 | 큰 글에는 전문 용어를 쓰지 않는다. 쓰면 바로 아래 한 줄로 푼다 | FR-13 |
| 가상 표시 | 시연 장면의 "가상 숫자예요" · "연습"은 가리지 않는다 | FR-10 |
| 한 장 한 메시지 | 슬라이드 제목은 주제가 아니라 **말하려는 결론 한 문장** (예: "판정은 코드가 하고 Claude는 설명한다") | 일반 원칙(이 팀이 정한 것은 아님) |
| 인터뷰 | 응답자 이름 · 연락처 · 소속 · 기수는 슬라이드에도 쓰지 않는다 — `응답자 A` | [security-records.md](../../.claude/rules/security-records.md) 2절 |

- 색 값 · 글꼴 · 간격은 정하지 않았다. 슬라이드 디자인은 앱의 얼음 파랑 테마를 따르고, 구체적인 도구(PowerPoint · Figma · 아티팩트 등)는 고한결이 고른다.
