## Context and Problem Statement

Navigator를 쓰는 사람(깃허브 아이디가 있고 Claude를 구독한 AI 입문자)은 Claude의 코딩 능력으로 프로그램을 만든다. 그런데 "만들어 줘"로 바로 코딩하면 구조가 비고, 무엇을 만들었는지 놓치고, 이해하지 못한 채 쌓인다. **Claude가 코드를 쓰되, 순서와 범위는 구조(Navigator)가 정하는** 방식이 필요하다.

## Considered Options

1. **자유 대화** — 사용자가 Claude에게 자유롭게 요청한다. 구조는 사람 기억에 맡긴다.
2. **요구사항 하나 = 한 바퀴 (제안)** — 준비(목적·요구·우선순위·구조·뼈대·추적표)를 마친 뒤, 가장 앞의 미완료 Must를 골라 이해 확인 → 시험 먼저 → 작게 구현 → 직접 확인 → 기록을 돈다.
3. **전체 한 번에 생성 후 검수** — 요구 목록을 주고 Claude가 한꺼번에 만든 뒤 사람이 검수한다.

## Decision Outcome (제안)

**Claude 제안: 2.** 준비를 마치기 전에는 코드를 쓰지 않는다.

### 준비 (프로젝트당 한 번)

| # | 만드는 것 | 기존 틀 |
|---|---|---|
| P1 | 목적·누가 쓰나 (한 문장) | 1단계 문제 저장 |
| P2 | 요구사항 목록 + 번호 + 완료 기준 | EARS, 번호 체계 |
| P3 | 우선순위 | MoSCoW |
| P4 | 구조 결정 한 장 | 3단계 ADR |
| P5 | 끝에서 끝까지 도는 가장 작은 흐름 | 4단계 Walking Skeleton |
| P6 | 요구↔코드↔시험 추적표(빈 칸으로 시작) | RTM |

### 한 바퀴 (요구사항 하나마다)

| 단계 | 일 | 누가 | 완료 조건 |
|---|---|---|---|
| 1 고르기 | 가장 앞의 미완료 Must | Navigator가 계산(AI가 고르지 않음) | 요구 번호 하나 |
| 2 이해 | 쉬운 말 설명 → "이해하셨나요?" | Claude 설명, 사람 답 | 사람이 "예"(FR-4·13) |
| 3 시험 먼저 | 완료 기준을 시험으로, 위반 시도부터 | Claude 초안, 사람 확인 | 시험이 실패한 채로 있음 |
| 4 작게 구현 | 시험을 통과시키는 최소 코드 | Claude | 시험 통과, 범위는 이 요구까지 |
| 5 직접 확인 | 사람이 실제로 실행해 봄 | 사람 | 자동 시험과 따로 기록 |
| 6 리뷰·기록 | 승인 → 추적표 갱신 → 배운 것 한 줄 | 사람 승인, Navigator 기록 | 요구↔코드↔시험 연결(FR-8) |

"아니요"는 모르는 곳을 묻는 질문으로 갔다가 같은 단계로 돌아온다(FR-5, 반복 상한은 11절 미정 값).

### 지키는 장치

| 위험 | 장치 |
|---|---|
| 요구 밖으로 코드가 번짐 | 한 바퀴에서 건드릴 파일 범위를 요구 번호에 묶는다 |
| 시험 없이 커밋 | 시험 실패 시 커밋 차단(기존 훅) |
| 새 아이디어가 끼어듦 | 구현하지 않고 새 번호로 목록에만 추가 |
| AI가 "충족"을 지어냄 | 근거 구절을 코드로 검증, 단계는 코드가 계산(규칙 검토 보완 ①②) |
| 한 바퀴가 너무 큼 | 크기 상한을 넘으면 요구를 쪼개도록 안내 |

## Consequences

- 완료 기준이 시험으로 바뀔 수 있는 문장이어야 한다(EARS 문형이 이미 이를 요구한다).
- 사용자는 코드를 직접 짜지 않지만, 단계 2·5·6에서 반드시 사람의 판단이 들어간다.
- 시연은 한 바퀴를 한 번 도는 것으로 보일 수 있다.
- 한 바퀴의 크기·확인 강도 때문에 느려질 수 있다 — 입문자에게는 이 느림이 이해를 쌓는 비용이다.
