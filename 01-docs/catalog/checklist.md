# 분석 체크리스트

7단계(유지보수)에서 놓쳤던 요구사항 유형이 쌓이는 곳. 2단계(문제 분석)에서 매번 이 목록을
확인합니다. [성장 로그](../00-overview/growth-log.md)에서 같은 유형이 3회 반복된 지적도
여기로 승격됩니다 — 그때는 절 제목에 "(성장 로그에서 승격, 날짜)"를 붙입니다.

## 기본 체크리스트 (IEEE 830 기반 시작점)

- [ ] 각 요구사항 문장에 동작이 하나만 담겨 있는가?
- [ ] 정성적 표현("빠르다", "편하다") 대신 측정 가능한 기준으로 썼는가?
- [ ] 엣지 케이스(빈 입력, 최대/최소 경계값, 동시성)를 나열했는가?

## 2단계 진입 전 확인 (Two Sum 드라이런에서 발견, 2026-09-17)

- [ ] 2단계 5단계 파이프라인(BABOK/EARS/Planguage/Kano/RTM)을 이 문제/프로젝트에
      **전부** 적용할지, 아니면 **경량화**할지 먼저 정했는가? — 알고리즘 트랙의
      단순 문제(예: Two Sum)는 보통 1단계 템플릿의 "입력 형식+제약조건"만으로
      충분하고, 무거운 파이프라인 전체를 돌릴 필요가 없다. 근본원인: 2단계
      파이프라인은 이 워크플로우 시스템 자체(프로젝트 트랙) 사례로만 검증되고
      확정됐고, 알고리즘 트랙에 실제로 적용해본 적이 없었다.

## 2단계 파이프라인 체크리스트 (01-docs/02-problem-analysis 참조, 전체 적용 시)

- [ ] 기능 요구사항이 EARS 5가지 문형(Ubiquitous/Event-driven/State-driven/Unwanted/
      Optional) 중 하나로 작성됐는가?
- [ ] 비기능 요구사항마다 Planguage의 Scale/Meter/Goal이 채워졌는가?
- [ ] 요구사항마다 MoSCoW와 Kano 분류가 둘 다 되어 있는가?
- [ ] 요구사항이 5개 이상이면 RTM(추적 매트릭스)이 작성됐는가?

## 3단계 파이프라인 체크리스트 (01-docs/03-pattern-analysis 참조)

- [ ] 후보를 표준 카탈로그(알고리즘 4대 패러다임 / 아키텍처 5대 스타일)에서 먼저 찾아봤는가,
      아니면 감으로 골랐는가?
- [ ] 후보가 2개 이상인데 ATAM 비교표 없이 넘어가지 않았는가?
- [ ] 프로젝트 트랙 결정이면 ADR로 남겼는가? (번호/상태/불변성 규칙 준수)
- [ ] 선택 근거(왜 이걸 골랐는지) 한 줄이 남아 있는가?
- [ ] **프로젝트 원칙표 점검** — 프로젝트 고유 제약(쓸 수 있는 도구·저장소, 금지 사항, 단일 지점 규칙 등)을
      `P1…Pn | 준수 여부 | 비고` 표로 적고 이번 결정과 대조했는가? **설계를 마친 뒤 한 번 더** 대조했는가?
      (출처: Intent-Specify(코딩마라톤 팀 과제, 사용자 채택 2026-10-04), plan.md "Constitution Check")
- [ ] **(화면이 있으면, 없으면 "해당 없음")** 화면 원칙을 요구·게이트·규칙에서 **역산**해 원칙마다 근거를 붙였는가?
      **"원칙이 배제한 흔한 선택"** 표(예: 차단을 토스트로 알리기, 미확정을 회색 placeholder로 두기)를 붙였는가?
      막힌 자리는 이유와 푸는 법을 함께 보이는가? (출처: Intent-Specify(사용자 채택 2026-10-04), SD_02 §1 — 원칙은
      [UI 패턴 카드](patterns.md)와 꺼내 쓸 것 *(V1에만 있음)*)

## 4·5단계 구현 체크리스트 (Intent-Specify(코딩마라톤 팀 과제, 사용자 채택 2026-10-04))

- [ ] **작업 목록 표기** — 작업마다 `[P]`(다른 파일을 건드리고 끝나지 않은 작업에 의존하지 않아 병렬 가능),
      어느 요구·스토리의 작업인지, **테스트 작업을 구현 작업 앞에** 두었는가? 첫 흐름에 필요한 작업 묶음(MVP)을 표시했는가?
- [ ] <!-- claude-drafted: 2026-10-21 --> **작업마다 범위 계약** — 고쳐도 되는 파일 · **건드리면 안 되는 파일** · 되돌리는 법 · 사람 확인이 필요한 일(병합 · 삭제 · 밖으로 보내기)을
      적었는가? 다른 작업과 주고받는 이름(받는 것 · 주는 것 — 함수 · 칸 이름)을 적었는가? 끝나면 바뀐 파일이 그 범위 안인지 diff로 본다
      (출처: [후보 장부](reference-candidates.md) W-37 — ai-engineering-from-scratch 36강, superpowers `writing-plans`, 이재엽 채택 2026-10-21)
- [ ] **EARS → Given-When-Then** — 확정 요구마다 [패턴별 최소 시나리오](../02-problem-analysis/02-specification-ears.md)를
      만들고, Then의 수치가 확정 값과 글자 그대로 같은가?
- [ ] **제약은 위반 시도로 확인** — 데이터 제약·권한 규칙·게이트마다 **일부러 어기는 입력**을 넣어 거부되는지 확인했는가?
      재실행해도 같은 결과인가(멱등)? 확인하지 않은 제약은 주석과 같다.
- [ ] **아키텍처 규칙은 도구로 강제** — "이 모듈만 외부 API를 부른다" 같은 규칙을 린트·테스트로 막았는가?
      ([code.md](../../.claude/rules/code.md) 6번)
- [ ] **(화면이 있으면)** 휴대폰 폭(390px)에서 가로 스크롤이 없고 접근성 자동 검사(axe, WCAG 2 AA) 위반이 0인지
      **E2E 테스트 하나로** 확인하는가? 색 대비는 눈이 아니라 검사로 본다 (출처: Intent-Specify(사용자 채택 2026-10-04) — 대비 미달 색을 이걸로 찾았다.
      예시: responsive-a11y.spec.ts *(V1에만 있음)*)

## 6단계 성능 실측 체크리스트 (Two Sum 벤치마크에서 발견, 2026-09-19)

- [ ] 벤치마크의 "최악 케이스" 입력이 **실제로 실행해서** 의도한 분기(예: 브루트포스가
      끝까지 가야 찾는 정답)를 타는지 숫자로 확인했는가? — Two Sum 벤치마크 초안은
      "정답을 배열 끝에 둔다"고 짰지만, 다른 원소 조합이 우연히 같은 합이라 브루트포스가
      앞에서 먼저 찾아버려 겨우 10배 차이로 나왔다. 근본원인: 벤치마크 코드도 구현이라
      결과를 실행해서 검증해야 하는데, "논리적으로 최악 케이스처럼 보인다"는 사고만으로
      끝냈다.

## 저장소 정합성 체크리스트 (gates.md DoD 점검에서 발견, 2026-09-19)

- [ ] 규정 문서(`gates.md` 등)의 한 항목을 등급/트랙별로 분기시켰다면, **같은 유형의
      가정이 다른 단계 항목에도 있는지 전체를 훑었는가?** — PRD/DoD 분기(1단계)를
      고칠 때 1단계만 고치고 넘어갔더니, 5·6단계 DoD에도 똑같이 Full 등급 전제가
      남아있던 걸 나중에야 발견했다. 근본원인: "고친 곳만" 검증했지, 동일 결함이
      수평으로 퍼져 있는지 훑는 절차가 없었다.
- [ ] 새 트랙(또는 새 파일명 관례)의 코드를 추가했다면, 공용 도구(예:
      `04-tests/run_all_tests.py`)가 그 트랙도 자동으로 처리하는지
      확인했는가? — 카탈로그 검색 CLI(프로젝트 트랙)를 추가하기 전까지
      `run_all_tests.py`는 `test_solution.py`(알고리즘 트랙 관례)만 찾도록
      하드코딩돼 있었다.

## 2단계 명세 품질 체크리스트 (카탈로그 검색 CLI 회고에서 발견, 2026-09-19)

- [ ] EARS 요구사항의 "충족기준"을 나중에 테스트로 옮길 사람(미래의 나 포함)이
      **무엇을 비교해야 하는지**(동작이 성공했는가 vs 출력값 자체가 같은가)까지
      구체적으로 적었는가? — "대소문자 혼합해도 동일한 결과를 냄"이라고만 적었더니,
      "동일한 결과"를 "출력 문자열이 완전히 같다"로 잘못 해석해서 틀린 테스트를 짰다.

## 세션 시작 체크리스트 (Best Time to Buy and Sell Stock 회고에서 발견, 2026-09-22)

- [ ] 세션을 시작하면 (또는 작업 디렉터리가 바뀌었다는 신호를 보면) `git status`가
      정상 응답하는지 먼저 확인했는가? — 실패하거나(`.git` 손상) 있어야 할 파일이
      없으면, 로컬을 고치려 하지 말고 **원격(GitHub)에서 다시 클론해서 복구**한 뒤
      진행한다. 근본원인: 이 세션이 실행되는 스크래치 워크스페이스는 세션 사이에
      재구성될 수 있는 환경이고, 그 동기화가 항상 완전하다는 보장이 없다 — 이
      시스템의 진짜 산출물은 로컬 파일이 아니라 푸시된 원격 저장소에 있다는 전제를
      명시적으로 세워둔 적이 없었다.

## 자기 참조 도구 체크리스트 (진행상황 대시보드 생성기 회고에서 발견, 2026-09-22)

- [ ] 이 저장소 자신의 상태(테스트 스위트, 파일 트리, git 이력 등)를 다루는
      도구를 만들 때, 그 도구 자신도 그 상태의 일부가 되어 자기 참조·무한
      재귀를 일으킬 수 있는지 먼저 따져봤는가? — 대시보드의 테스트 결과
      수집기가 `run_all_tests.py`를 기본값으로 다시 실행하면, 그 실행이
      수집기 자신의 테스트 파일을 재발견해서 재귀 호출될 수 있었다. 설계
      단계에서 의존성 주입(가짜 loader)으로 미리 끊어뒀지만, 이런 도구를
      또 만들면 같은 패턴이 재발할 수 있다.

## 단계별 보안 점검 체크리스트 (세컨드 브레인 1→2 게이트에서 사용자가 발견, 2026-10-01)

게이트마다 DoD와 함께 **해당 단계의 항목**을 확인한다([gates.md](../00-overview/gates.md) "보안 점검").
기준 문서는 [기록·보안 기준](../../.claude/rules/security-records.md)이다. 해당 없는 항목은 지우지 말고
"해당 없음 — 이유"를 게이트 로그 근거 칸에 적는다.

- [ ] **1단계** 다룰 데이터의 종류, 다른 사람의 정보가 섞이는지, 무엇이 밖으로 나가는지(AI 서비스, 외부
      도구, 공유 링크)를 기록·보안 기준과 대조해 세션 파일에 적었는가?
- [ ] **2단계** 보안 요구를 요구사항 문장으로 썼는가(예: EARS Unwanted "If 계정 내용이 밖으로 나가려 하면,
      then …")? 기록의 민감도와 보관·삭제 기간을 정했는가? **자동화가 실패할 때의 동작**(알림, 재시도 상한,
      빠진 것 표시, 실행 기록)을 요구사항으로 썼는가? (기록·보안 기준 6-1)
- [ ] **3단계** 위협(무엇으로부터 지키는가), 권한(필요한 만큼만), 인증, 저장 위치를 대안 비교·ADR의
      기준에 넣었는가?
- [ ] **3단계(서버·API가 있으면)** 요청 판정 순서(인증 → 권한 → 소유권 → 게이트)와 층별 거부 응답을 표로 정했는가? (6-3)
- [ ] **4·5단계** 비밀값(API 키, 토큰, 비밀번호)이 코드·문서·커밋에 없는가? 다른 사람의 정보는 저장하지
      않거나, 프로젝트가 정한 최소 범위(예: 세컨드 브레인 — 이름·직책·한 줄)를 넘지 않았는가? AI가 만든 부분에 **어떻게 확인했는지**를 남겼는가? (6-2) 비밀값 검사(6-3)를
      통과했는가?
- [ ] **6단계** 공개 여부, 공유 링크, 외부 도구로 무엇이 노출되는지 점검했는가? 밖에 공개한 서버·API·페이지에
      **인증이 있는가?** (6-3) 실측에 **실제로 써 본 기록**이 있고, 증빙 스크린샷에 키·이메일·다른 사람 정보가
      없는가? (6-2)
- [ ] **7단계** 회고에 보안 사건이나 아찔했던 일(근접 사고)을 적었는가? 자동화 실행 기록에서 실패·재시도가 있었는지 돌아봤는가? (6-1)

근본원인: 게이트 기준에는 보안 항목이 1단계 PRD의 `Security & Compliance` 칸 하나뿐이었다. 그 칸은
Full 등급이 PRD로 확장할 때만 생기고, 2단계 이후에는 보안을 꺼내 보는 시점이 없었다. 사용자가
"우리 워크플로우에 보안 사항들을 채크하기 위한 내용이 조금 들어가야할거 같아"라며 게이트를 Hold했다.
비밀값 검사는 커밋 전 검사 훅으로 만들기로 사용자가 정했다(2026-10-01, 기록·보안 기준 6-3). 2026-10-01에 6-1·6-2·6-3
항목을 더했다 — 출처는 사용자가 만든 저장소들(세컨드 브레인 참고 자료)이다.
