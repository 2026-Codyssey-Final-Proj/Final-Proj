단계 번호는 모두 **화면의 번호**(1 ~ 8단계)다. 코드(`03-backend/navigator/navigator.js`)는 0부터 센다.

## 1. 가설 — 무엇을 검증하나

### 1-1. 출발점

[기획안](../00-overview/final-project-plan.md) "문제"는 바이브 코딩을 하는 사람이 ① AI가 만든 결과가 맞는지, 지금 어느 단계이고 다음에 무엇을 할지 몰라 **중도에 멈추고**, ② 끝까지 만들어도 **내 코드를 설명하지 못한다**고 본다. Floe는 이 둘을 돕겠다는 제품이다.

그런데 "Claude Code만 써도 되지 않나?"([기획 정리](../00-overview/기록/기획-정리-2026-10-24.md) 문답 3)라는 물음이 남는다. Floe만 써 보게 해서는 이 물음에 답하지 못한다 — 잘 끝나도 그 사람이 원래 잘했는지 가를 수 없다. 그래서 이 계획은 **Claude Code만 쓸 때(A)와 Floe를 같이 쓸 때(B)를 같은 사람에게서 맞댄다**(2절).

### 1-2. 가설 셋

> **큰 가설:** Floe를 같이 쓰면, 바이브 코딩을 하는 초심자가 Claude Code만 쓸 때보다 **덜 멈추고, 만든 것을 설명하고, AI의 결과를 확인하고 쓴다.**

| 가설 | 문장 | 기획안 문제 | 무엇으로 보나(3절) | 지지한다고 보는 때 [제안] | 지지하지 못한다고 보는 때 |
|---|---|---|---|---|---|
| **H1 멈춤** | B에서 **더 멀리 가고 덜 멈춘다** | ① 뒤쪽 — 다음에 무엇을 할지 몰라 멈춘다 | 간 단계(같은 체크리스트) · "다음에 뭘 해요?" 횟수 · 멈춤 횟수 | B에서 **5명 중 4명 이상**이 화면 5단계까지 가고(11-1), 짝 비교에서 "B가 더 멀리"가 "A가 더 멀리"보다 많다 | 둘 중 하나라도 아니면 |
| **H2 설명** | B로 만든 뒤 **만든 까닭을 더 잘 설명한다** | ② 설명하지 못한다 | 1분 설명(이유 2개 이상) | B에서 **5명 중 3명 이상**(11-1), 짝 비교에서 "B가 나았다"가 "A가 나았다"보다 많다 | 둘 중 하나라도 아니면 |
| **H3 확인** | B로 만든 뒤 **AI가 "다 됐다"고 해도 직접 확인해 틀린 곳을 찾는다** | ① 앞쪽 — AI가 만든 결과가 맞는지 판단하지 못한다 | 검토 과제(2-7) — 심어 둔 틀린 곳을 찾았나 | 짝 비교에서 "B 뒤에만 찾았다"가 "A 뒤에만 찾았다"보다 많다. **숫자 목표는 미정**(11-1에 없다 — 6절 7번) | 같거나 반대면 |

- **지지 기준은 시험 전에 정하고 바꾸지 않는다.** 결과를 보고 기준을 바꾸면 원하는 답을 만들 수 있다. 리허설 뒤에 바꿀 때는 사용 테스트 **전에** 바꾸고 [요구사항](../00-overview/requirements.md) 13-1에 적는다.
- 세 가설은 따로 판정한다 — 하나가 지지돼도 나머지는 그 결과대로 적는다.

### 1-3. 전제 — 가설보다 먼저 맞아야 하는 것

Floe의 판정이 틀리면 B 조건 자체가 무너진다. 사람 없이 잴 수 있어 **리허설 전에** 잰다.

| 전제 | 어떻게 재나 | 지난 값 | 목표(11-1) |
|---|---|---|---|
| AI 판정 일치율 | `03-backend/navigator/live-check.js --all --report` | 98% (2026-10-18) · 100% (2026-10-24, [기록](../verification/live-check-2026-10-24.md)) | 95% 이상 |
| 판정 한 번의 토큰 | 같은 점검의 토큰 칸 | 평균 8,042 (2026-10-18) → 4,729 (2026-10-24) | 한 번 8,000 이하 |

### 1-4. 이 시험이 확인하지 않는 것

| 무엇 | 왜 빼나 |
|---|---|
| 배운 것이 **다음 프로젝트로 이어지는가**(기획안 문제 ② 뒤쪽) | 한 번의 시험으로 잴 수 없다 — 몇 주 뒤 다시 만나야 한다 |
| 익숙해진 사람이 **Floe에 기대게 되는가**([기획 정리](../00-overview/기록/기획-정리-2026-10-24.md) 문답 4) | 처음 쓰는 사람만 본다. 끝 질문(4-3)에서 "다음에 혼자 만든다면"으로 말만 남긴다 |
| 난이도별 차이 | 난이도마다 1 ~ 2명이라 말할 수 없다 — 난이도는 각자에게 알맞은 과제를 주는 장치로만 쓴다 |

## 2. 실험 설계 — 어떻게 입증하나

### 2-1. 이 시험의 성격

웹 서비스의 A/B 테스트는 수천 명을 무작위로 두 무리로 나누고 통계로 판정한다. 우리는 5명 안팎이라 그렇게 하지 못한다. 이 시험은 **같은 사람이 두 조건을 해 보는 작은 비교 사용성 시험**(within-subject)이고, 줄 수 있는 답은 "증명"이 아니라 **"이번 5명에서는 이렇게 달랐고, 그 까닭은 녹화에서 이것이었다"**다.

좋은 비교 시험의 기준과 이 계획의 대응:

| 기준 | 이 계획 |
|---|---|
| 물음을 먼저 정한다 | 1-2의 가설 셋 · 지지 기준 |
| A와 B의 차이는 하나뿐 | Floe를 켜느냐만 다르다(2-6) |
| 재는 것 · 합격선을 먼저 정한다 | 3절 · 1-2 — 시험 전에 고정 |
| 치우침을 막는다 | 같은 사람이 둘 다 · 네 가지 순서(2-4) · 같은 짜임의 과제 짝(2-5) |
| 채점은 결과를 모르는 사람이 | 진행자가 아닌 사람이 녹화로 채점(3-2) — 조건은 녹화에 보여 반쯤만 |
| 사람이 충분하다 | **약함** — 5명 안팎. 사람 수로만 말한다(8절) |
| 먼저 한 번 돌려 본다 | 리허설(5절) |
| 실패도 그대로 적는다 | 지지하지 못함 · 하지 못함을 그대로(4절 · 8절) |

### 2-2. 조건

| 조건 | 무엇을 쓰나 |
|---|---|
| **A — Claude Code만** | 참여자의 Claude Code 하나. Floe는 끈다 |
| **B — Floe와 같이** | 같은 Claude Code + Floe 섬, **진짜 AI 모드** — 연습 모드는 정해진 장면(동아리 행사 신청 앱)만 알아 다른 과제로는 돌지 않는다(`03-backend/navigator/scenario.js` — "여기 없는 입력은 살펴보지 않는다") |

### 2-3. 참여자

- **5명 이상**, 비전공자를 넣는다(11-1, 기획안 "검증 계획"). 다른 유형(학생 · 직장인 · 창작자)을 넣을지는 6절 6번.
- 시험 전에 두 가지만 묻는다 [제안] — 난이도를 정하고(2-5), 해 본 과제를 뺀다.
  - "AI로 프로그램을 만들어 본 적이 몇 번 있나요?" — 없음 → 하 · 1 ~ 2번 → 중 · 3번 이상 → 상
  - "이 과제를 해 본 적이 있나요?"(코디세이 과제 등) — 해 봤으면 다른 짝
- 기록에는 이름 · 연락처를 쓰지 않는다 — `참여자 A`처럼 가린다. 화면 녹화는 동의를 받고 한다.

### 2-4. 순서와 짝 — 과제 · 조건 · 순서가 섞이지 않게

사람마다 같은 짝의 과제 둘(2-5)을 하나는 A, 하나는 B로 한다. 익숙함(둘째가 쉬움)과 과제 차이(한쪽이 쉬움)가 "Floe 덕분"으로 보이지 않게 **네 가지 순서**를 돌려 쓴다.

| 순서 | 첫째 | 둘째 |
|---|---|---|
| ① | 과제 1 · A | 과제 2 · B |
| ② | 과제 2 · A | 과제 1 · B |
| ③ | 과제 1 · B | 과제 2 · A |
| ④ | 과제 2 · B | 과제 1 · A |

참여자 순서대로 ① → ② → ③ → ④ → ① … 을 준다. 5명이면 ①이 두 번 — 결과에 적는다.

### 2-5. 과제

**모든 과제의 기준:** ① 비전공자에게 익숙한 일상 ② 밖의 서비스 · 로그인 · 서버가 없다(웹 페이지 하나, 상은 화면 둘까지, 브라우저에만 저장) ③ Floe가 답을 미리 알지 않는다(**동아리 행사 신청 앱은 쓰지 않는다**) ④ 끝은 화면의 **5단계 '뼈대 먼저 이어 보기'** — 가장 단순한 흐름이 실제로 도는 데까지.

**난이도는 짜임으로 가른다**

| 난이도 | 짜임 | 시간 [제안] |
|---|---|---|
| 하 | 입력 2칸 · 목록 · 숫자 하나(개수나 합계) | 30분 |
| 중 | 입력 3 ~ 4칸 · 분류별 합계 · 고치기 · 지우기 | 40분 |
| 상 | 중 + 계산 규칙(나누기 · 비율 · 고르기) 또는 화면 둘 | 50분 |

**후보 — 한 사람이 받는 두 과제는 같은 줄의 짝**(같은 난이도 · 같은 짜임)

| 짝 | 과제 1 | 과제 2 | 비고 |
|---|---|---|---|
| **하-1 [권함]** | 독서 기록장 — 책 이름 · 별점 → 목록, 읽은 권수 | 용돈 기입장 — 쓴 곳 · 금액 → 목록, 남은 돈 | |
| 하-2 | 물 마시기 기록 — 시각 · 양 → 목록, 오늘 마신 양 | 할 일 목록 — 할 일 · 중요도 → 목록, 남은 할 일 수 | 예비 |
| 하-3 | 프롬프트 모음장 — 제목 · 프롬프트 글 → 목록, 모은 개수 | 레시피 모음장 — 요리 이름 · 만드는 법 → 목록, 모은 개수 | 과제 1은 코디세이(아래) |
| **중-1 [권함]** | 가계부 — 날짜 · 분류 · 내용 · 금액 → 목록, 분류별 합계, 고치기 · 지우기 | 운동 기록표 — 날짜 · 운동 · 시간 · 강도 → 목록, 운동별 합계 시간, 고치기 · 지우기 | |
| 중-2 | 냉장고 정리 — 음식 · 칸 · 넣은 날 · 양 → 칸별 개수, 고치기 · 지우기 | 옷장 정리 — 옷 · 종류 · 계절 · 색 → 종류별 개수, 고치기 · 지우기 | 예비 |
| **상-1 [권함]** | 여행 경비 나누기 — 누가 · 무엇에 · 얼마 → 누가 누구에게 얼마 | 공부 시간 목표표 — 과목 · 목표 · 한 시간 → 과목별 달성률 | |
| 상-2 | 가계부 + 예산 — 분류별 예산, 넘으면 알림 · 요약 화면 | 운동 기록 + 목표 — 주별 목표, 달성 여부 · 요약 화면 | 예비 · 중-1과 같은 사람에게 주지 않는다 |
| 상-3 | 냉장고 털이 셰프 — 재료를 고르면 미리 넣은 레시피 10개 중 만들 수 있는 것 | 여행지 고르기 — 지역 · 취향을 고르면 미리 넣은 여행지 10곳 중 맞는 곳 | 둘 다 코디세이 과제의 줄인 판(아래) |

**코디세이 과제에서 온 후보** — 과정에서 실제로 낸 과제라 현실에 가깝다. 원문은 옮기지 않는다.

| 코디세이 과제 | 원래 만든 것(한 줄) | 쓰는 법 |
|---|---|---|
| AI 활용 학습 01 · Python 및 Git 기초 | 프롬프트를 저장 · 찾는 콘솔 프로그램 | 웹 페이지로 바꿔 **하-3** |
| AI 활용 학습 03 · AI 웹 개발 | 냉장고 재료로 요리를 추천하는 웹 서비스(AI API · 배포) | AI 대신 미리 넣은 레시피 목록으로 줄여 **상-3** |
| AI 활용 학습 02 · Python 응용 API | 지역 · 맛집 정보로 여행지를 추천하는 프로그램(외부 API) | API 대신 미리 넣은 여행지 목록으로 줄여 **상-3** |
| AI 응용 학습 01 · 02, AI 도구 학습 | 데이터 분석 보고서 · 서버와 DB가 있는 AI 비서 · 영상 · 디자인 시안 | 쓰지 않는다 — 앱이 아니거나 서버 · DB · 밖의 AI가 필요하다 |

코디세이 과제는 마감이 있어 인터뷰의 "끝낸 비율"(Q5)이 스스로 시작한 일보다 높게 나올 수 있다 — 기준선과 맞댈 때 적는다(인터뷰 질문지 메모).

**과제 카드** [제안] — 참여자에게 보이는 것은 한 문단뿐이다(가계부 예).

> 돈을 쓸 때마다 날짜, 분류(식비 · 교통 · 생활 · 기타), 무엇을 샀는지, 금액을 적어 두는 작은 웹 페이지를 만들어 주세요. 적은 것은 목록으로 보이고, 분류마다 얼마 썼는지 합계가 보여야 합니다. 잘못 적은 것은 고치거나 지울 수 있어야 합니다. 40분 동안 할 수 있는 데까지 해 보세요.

### 2-6. 같은 조건으로 맞추는 것 — A와 B의 차이는 Floe 하나

| 맞추는 것 | 어떻게 | 까닭 |
|---|---|---|
| AI | A · B 모두 같은 Claude Code 계정 · 모델 | AI 차이가 Floe 차이로 보이지 않게 |
| 시간 | 한 사람의 두 과제는 같은 시간(2-5) — 넘으면 멈추고 간 데까지 기록 | "완주"가 시간 싸움이 되지 않게 |
| 시작 | 빈 폴더 · 같은 모양의 과제 카드 · 같은 안내 2분 [제안] | 출발선을 같게 |
| B의 안내 | Floe를 처음 쓰는 사람에게 섬 쓰는 법 1분 [제안] — 과제 시간에 넣지 않는다 | 처음 보는 도구라 불리하지 않게, 그러나 과제 힌트는 주지 않게 |
| 진행자의 말 | 막혀서 물으면 정해 둔 한 마디만 — "화면(또는 AI)에게 물어보세요" | 진행자가 길을 알려 주면 차이가 사라진다 |
| 기록 | 화면 녹화(동의) + 진행자 기록표 | 나중에 다시 센다 |

### 2-7. H3 검토 과제 — "다 만들었어요"를 확인하나

비전공자에게 코드를 읽게 하지 않는다. **과제마다 끝에**, 그 과제와 같은 페이지를 미리 만들어 **틀린 곳을 하나 심어 두고**, AI가 한 말처럼 이렇게 보여 준다 [제안].

> AI: "다 만들었어요. 잘 동작합니다." — 이 페이지를 그대로 써도 될까요? 3분 동안 직접 써 보고, 고칠 곳이 있으면 말해 주세요.

**짝의 두 과제에는 같은 종류 · 같은 크기의 틀린 곳**을 심는다 — 어느 쪽이 더 찾기 쉬우면 H3이 Floe가 아니라 과제 차이를 잰다.

| 짝 | 과제 1에 심는 것 | 과제 2에 심는 것 | 종류 |
|---|---|---|---|
| 하-1 | 별점에 0이나 9를 넣어도 그대로 저장된다 | 금액에 0이나 음수를 넣어도 그대로 저장된다 | 허용 범위를 막지 않음 |
| 중-1 | 한 줄의 "지우기"를 누르면 **맨 위 줄**이 지워진다 | 같은 것 | 다른 줄이 바뀜 |
| 그 밖의 짝 | 리허설 전에 같은 규칙으로 만든다 — 미정(6절 9번) | | |

- 이 페이지는 참여자가 만든 것이 아니라 **미리 만든 같은 페이지**다 — 참여자마다 다르면 비교가 안 된다.
- 첫 검토 과제를 한 뒤에는 "틀린 곳이 숨어 있다"는 것을 알게 된다. 네 순서(2-4)가 이 영향도 A · B에 반씩 나눈다.

## 3. 측정과 채점

### 3-1. 무엇을 재나

| 가설 | 재는 것 | 어떻게 재나 | 조건 |
|---|---|---|---|
| H1 | **간 단계** — 화면 1 ~ 5단계 할 일 23개(`navigator.js` 단계 0 ~ 4) 중 채운 칸, 5단계까지 갔나 | 같은 체크리스트(3-2)로 녹화를 보고 | A · B |
| H1 | **"다음에 뭘 해요?"** — 진행자에게 다음 할 일을 물은 횟수 | 녹화에서 센다 | A · B |
| H1 | **멈춤** — 다음 행동 없이 멈춘 횟수 | 녹화에서 센다 — 몇 초를 멈춤으로 볼지는 미정(6절 3번) | A · B |
| H2 | **1분 설명** — "왜 이렇게 만들었나요?"에 1분 안에 이유 2개 이상 | 과제마다 끝에 같은 질문, 시간을 잰다 | A · B |
| H3 | **검토 과제** — 심어 둔 틀린 곳을 찾았나 · 직접 눌러 봤나 | 2-7, 녹화 | A · B |
| 참고 | 확인 질문 정답률(관문의 확인 질문) | 화면 기록 | B만 — 목표 70% 이상(11-1) |

### 3-2. 채점 규칙

- **"어디까지 갔나"는 A · B 모두 같은 체크리스트**로 본다 — Floe의 단계 할 일을 종이 한 장으로 뽑아, A에서도 같은 칸을 체크한다. B의 화면 판정은 참고로만 쓴다(Floe가 스스로를 채점하지 않게).
- **채점은 진행자가 아닌 팀원 한 명**이 녹화를 보고 한다(이슈 #71 "만든 사람이 직접 채점하면 점검이 약해진다").
- **1분 설명의 "이유"로 세는 것** [제안]: 누가 쓰는지 · 왜 이 기능을 먼저 했는지 · 왜 이 방법을 골랐는지처럼 **결정의 까닭**. 기능을 나열한 것은 세지 않는다.
- **검토 과제** [제안]: **찾음** = 심어 둔 곳을 짚고 무엇이 틀렸는지 말함 · **일부** = 이상하다고만 함 · **못 찾음** = "그대로 써도 된다". H3 판정에는 "찾음"만 센다.

## 4. 결과 판정

### 4-1. 사람마다 짝으로

평균을 내지 않는다. 가설마다 사람별로 **"B가 나았다 / 같았다 / A가 나았다"**를 적고 사람 수로 더한다(예: 5명 중 4명은 B에서 더 멀리 갔다).

| | 참여자 A | 참여자 B | … | B가 나았다 | 같았다 | A가 나았다 |
|---|---|---|---|---|---|---|
| H1 간 단계 | | | | | | |
| H2 1분 설명 | | | | | | |
| H3 검토 과제 | | | | | | |

### 4-2. 가설마다 판정

1-2의 "지지한다고 보는 때"로만 판정한다 — **지지 / 지지하지 못함 / 하지 못함(재지 못함)**. 지지하지 못한 가설은 녹화에서 까닭을 찾아 한 줄로 적는다(예: "B에서 섬의 안내를 읽는 데 시간을 썼다").

### 4-3. 끝 질문 — 숫자가 놓친 것

- "둘 중 어느 쪽이 다음에 할 일이 더 분명했나요?"
- "다음에 혼자 만든다면 어느 쪽을 쓰겠어요? 왜요?"

## 5. 리허설 — 사용 테스트 전에

팀원 한 명이 **하-1과 중-1**을 A · B로 한 번씩 해 본다(상은 "3번 이상" 참여자가 있을 때만). 잴 것:

1. 과제 시간이 맞나 — 30 · 40분 안에 5단계에 닿을 수 있나
2. 짝이 정말 비슷한가 — 두 과제에서 간 단계가 크게 다르지 않나
3. 검토 과제의 틀린 곳이 너무 쉽거나 어렵지 않나
4. 진짜 AI 모드에서 한 사람에게 드는 토큰
5. 멈춤을 몇 초로 볼지 — 생각하느라 멈추는 시간을 녹화에서 본다

리허설 결과로 고친 것은 사용 테스트 **전에** 이 문서에 적는다.
