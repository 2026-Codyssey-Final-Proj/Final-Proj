# 평가 질의응답 — PREP 답변 카드 (문서 근거 초안)

질문 목록과 담당은 [expected-questions.md](expected-questions.md), 카드를 만드는 규칙은 [qa-prep 스킬](../../.claude/skills/qa-prep/SKILL.md)이다.

| 항목 | 내용 |
|---|---|
| 카드 수 | 19장 — 근거가 있는 답 14장(1~14) + 아직 못 한 일을 정직하게 답하는 카드 5장(15~19) |
| 근거 | 레포 문서 · 코드(`navigator.js` 등) · PR 기록. 카드마다 "출처" 줄 |
| 기준 | 60초 이내(약 5문장), 이유는 2개 이하 — qa-prep 정량화 기준 |
| 지금 상태 | **발표자가 확인하기 전의 초안.** "미확인"은 근거를 못 찾은 자리다 — 채우려고 지어내지 않았다 |
| 기준일 | 2026-10-24. 인터뷰(#11)는 보류 중이고 사용 테스트(#13)는 시작 전이다 |

*PREP은 출처 확인 불가, 실무에서 통용되는 후보 구조입니다.*

## 확인하는 법 (발표자가 한다)

각 카드를 소리 내어 읽고 **결론 · 이유 · 사례** 칸마다 예 / 아니오 / 일부로 판단한다. "아니오"인 칸은 지우고 "미확인"으로 되돌린다. 읽고 내 말로 설명할 수 없는 문장은 발표에서 빼거나 담당(이재엽 · 두승현)에게 먼저 묻는다.

## 1. AI 적용의 합리성

### 카드 1 — Q5 "API를 그대로 쓴 것과 무엇이 다른가요?"

| 칸 | 내용 |
|---|---|
| 결론 | Claude가 답을 정하게 두지 않고, **코드 규칙이 판정하고 Claude는 초안 · 설명을 맡는** 구조입니다. |
| 이유 1 | 같은 입력에 같은 판정이 나와야 시험할 수 있습니다 — 수용 테스트와 계약 테스트가 가능해집니다. |
| 이유 2 | Claude를 부르는 곳을 한 모듈로 모아 키 · 실패 처리 · 비용을 한곳에서 봅니다. |
| 사례 | Claude가 "이 항목을 했다"고 답해도, 코드가 그 근거 구절이 사용자 글에 **글자 그대로 있는지** 확인하고 없으면 "안 했다"로 바꿉니다. 지금 단계도 코드가 정합니다. |
| 결론(재확인) | 그래서 Claude를 쓰되 판정은 코드와 사람이 쥡니다. |
| 출처 | [ADR-0003](../03-pattern-analysis/adr/0003-ai-boundary-and-judgement.md) · `03-backend/navigator/navigator.js` 의 `parseJudgement`(근거 구절 확인) |
| 미확인 | 코드 규칙이 정확히 어디까지인지(항목별 충족 여부 자체는 Claude가 읽고 정한 뒤 코드가 검증하는 구조로 보인다) — **이재엽에게 한 번 확인** |

### 카드 2 — Q6 "왜 AI가 안 하고 코드 규칙이 판정하나요? AI가 더 유연하지 않나요?"

| 칸 | 내용 |
|---|---|
| 결론 | 유연함보다 **같은 입력에 같은 결과**가 더 중요해서 판정은 코드에 두었습니다. |
| 이유 1 | 같은 입력에 같은 판정이 나와야 수용 테스트 · 계약 테스트로 시험할 수 있습니다. |
| 이유 2 | 판정 규칙이 우리의 주력이라면 눈에 보이는 규칙이어야 합니다 — 프롬프트에만 맡기면 "API를 그대로 쓴 것"으로 보일 수 있습니다(기획 20점). |
| 사례 | 처음 설계 때 세 안(전부 프롬프트 / 코드 규칙 + Claude 초안 · 리뷰 / 사람만)을 비교해 둘째 안을 골랐습니다. 설계도의 질처럼 코드로 못 보는 것은 Claude 리뷰로 보이고 **통과 여부는 사람이 정합니다.** |
| 결론(재확인) | AI는 쓰이는 자리가 정해져 있고, 최종 판정은 규칙과 사람입니다. |
| 출처 | ADR-0003 "Considered Options" · FR-3 |

### 카드 3 — Q7 "AI가 틀리거나 지어내면 어떻게 막나요?"

| 칸 | 내용 |
|---|---|
| 결론 | **지어낸 근거는 코드가 걸러 내고**, 모르는 자리는 비워 두게 했습니다. |
| 이유 1 | Claude에게 "글에 적힌 것만 근거로 쓰고, 글자 그대로 따온 구절만 인용하라"고 요구하고, 코드가 그 구절이 사용자 글에 실제로 있는지 다시 확인합니다. 없으면 "했다"로 치지 않습니다. |
| 이유 2 | 시연 안전장치 S1~S6(알림 확인 값 · 받은 글 검사 · 기록 비우기 등)과, 보내기 전에 비밀번호 같은 모양을 찾아 멈추고 묻는 검사(`sensitive.js`)가 있습니다. |
| 사례 | 실제 AI로 연습 예시 9개를 점검했을 때, 달랐던 곳이 **6단계 2번 하나**였습니다(한 항목에 두 가지가 묶여 있었음). 그 항목을 나누는 쪽으로 고쳤습니다. |
| 결론(재확인) | 완벽하다고는 말하지 않고, 틀림이 **보이게** 만들고 걸러 내는 구조입니다. |
| 출처 | `navigator.js` 216~217행(프롬프트 규칙) · 315~331행(`found` · `parseJudgement`) · PR #98 · [team-priorities.md](team-priorities.md) 0절 |
| 미확인 | 설계도(초안 · 리뷰) 내용의 질을 사람 없이 어떻게 점검하는지 — PR #98도 "사람이 읽어야 한다"고 적었다 |

### 카드 4 — Q8 "정확도 98%는 무엇과 무엇을 비교한 숫자인가요?"

| 칸 | 내용 |
|---|---|
| 결론 | **연습 예시 9개**(0~7단계)를 실제 Claude로 판정시켜 **미리 달아 둔 정답 칸과 비교**했고, 칸 단위로 98% 일치했습니다. 사용자를 대상으로 잰 숫자가 아닙니다. |
| 이유 1 | 9개 모두 형식 통과, 호출 실패 0이었습니다. |
| 이유 2 | 달랐던 칸은 6단계 2번 하나였습니다. 한 항목에 "잰 값"과 "못 한 것"이 묶여 예시 글의 정답과 AI가 달랐습니다. |
| 사례 | 한 번 호출에 평균 약 8천 토큰이 들었고 이번 점검 전체는 72,375토큰이었습니다. |
| 결론(재확인) | 작은 표본의 일치도이고, 실사용 정확도는 사용 테스트에서 따로 봅니다. |
| 출처 | PR #98 본문(2026-10-18) · `01-docs/verification/live-check-2026-10-18.md`(PR 본문이 가리킴) |
| 주의 | "98%"만 떼어 말하지 말 것 — 표본(9개), 정답의 출처(연습 예시), 단위(칸)를 같이 말한다 |

### 카드 5 — Q9 "장기 기억은 AI 적용에 어떻게 도움이 되나요? 지금은 왜 서재 단추가 없나요?"

| 칸 | 내용 |
|---|---|
| 결론 | 배운 것과 정한 것이 **다음 프로젝트에서도 남도록** 마크다운 문서로 쌓는 구조이고, 지금 화면에서는 "책" 칸이 그 결과(README)를 보여 줍니다. |
| 이유 1 | 처음 문제가 "배운 게 다음에 이어지지 않는다"였고, 기억은 사람마다 따로 저장합니다. |
| 이유 2 | 의미 검색(RAG)은 비용과 일정 부담이 커서 키워드 · 태그 검색으로 시작하고, 검색을 한 인터페이스 뒤에 두어 나중에 바꿀 수 있게 했습니다. |
| 사례 | 2026-10-23에 서재 화면과 단추를 **지웠습니다**(코드는 남김, 대회가 끝나면 다시 엽니다). 책은 내 저장소 README를 받아 와 보여 주기만 합니다. |
| 결론(재확인) | 기억의 방식은 정했고, 보이는 화면은 대회 범위에 맞게 줄였습니다. |
| 출처 | [ADR-0004](../03-pattern-analysis/adr/0004-long-term-memory.md) · requirements FR-8 줄(2026-10-23) |
| 미확인 | RAG를 시연에서 보일지 — ADR-0004의 열린 질문, 이재엽 확인 |

### 카드 6 — Q10 "확정과 이해 여부를 왜 사람이 누르나요?"

| 칸 | 내용 |
|---|---|
| 결론 | 이 제품은 결과를 대신 만들어 주는 AI가 아니라 **사용자가 스스로 결정하도록 길을 안내하는** 내비게이터라서, 확정과 "이해했다"는 사람이 누릅니다. |
| 이유 1 | AI가 대신 확정하면 사용자는 이해하지 못한 채 넘어가고, 그게 원래 풀려던 문제(끝까지 만들어도 설명하지 못함)입니다. |
| 이유 2 | 확정 · 순서 · 이해 여부를 사람에게 두면 책임 소재와 학습의 주체가 분명합니다. |
| 사례 | 게이트에서 "예 / 아니요"로 묻고, "아니요"면 어디가 어려운지 → 질문 → 한 장 요약 → 다시 묻기를 거칩니다. "예" 전에는 다음 단계로 가지 않습니다. |
| 결론(재확인) | 성장하는 쪽은 AI가 아니라 사람이어야 해서 그렇게 했습니다. |
| 출처 | [기획안](final-project-plan.md) "목표" · FR-3 · FR-4 · FR-5 |

## 2. 기술 · 구조

### 카드 7 — Q11 "서버 없이 가상 데이터로 시연하는데, 어디까지가 가짜인가요?"

| 칸 | 내용 |
|---|---|
| 결론 | 서버 없이 이 컴퓨터에서 돌고, **Claude 호출은 실제**이며 가짜는 "한곳에서 보기"의 숫자 같은 가상 데이터입니다. |
| 이유 1 | 대회 시연은 환경 의존을 줄이려고 서버 · 도메인 없이 하기로 했습니다(FR-10). |
| 이유 2 | 가상인 곳은 화면에 **"가상 숫자예요" · "연습"**으로 표시해 가리지 않습니다. |
| 사례 | 미리 녹화한 Claude 답으로 재생하면 토큰 0으로 같은 화면이 나옵니다(판정 9 · 초안 4 · 다시 보기 4, 17개 녹화). 실제 호출은 키 또는 Claude 구독으로 돕니다. |
| 결론(재확인) | 진짜 AI를 쓰되, 시연이 어디서든 열리도록 구조를 잡았습니다. |
| 출처 | FR-10 · [ADR-0002](../03-pattern-analysis/adr/0002-demo-structure.md)(미리 만든 응답 + 실제 호출) · PR #98 |

### 카드 8 — Q12 "왜 Claude 구독이 기본이고 API 키는 선택인가요?"

| 칸 | 내용 |
|---|---|
| 결론 | 쓰는 사람이 **Claude만 구독한 입문자**여서, 키를 따로 만들게 하는 장벽을 없애려고 구독을 기본으로 했습니다. |
| 이유 1 | API 키를 직접 만드는 일이 입문자에게는 진입 장벽입니다. |
| 이유 2 | 서버를 두고 우리가 대신 호출하면 인증 · 비용 · 약관을 우리가 져야 해서, 각자 컴퓨터의 로그인에만 의존합니다. |
| 사례 | 순서는 ① 키가 있으면 그 키 → ② 이 컴퓨터에 로그인된 Claude Code(구독) → ③ 둘 다 없으면 연습용 예시. 로그인 정보는 저장 · 전송 · 중계하지 않습니다. |
| 결론(재확인) | 입문자가 바로 쓰게 하되 남의 구독 · 키를 대신 쓰지 않는 선택입니다. |
| 출처 | [ADR-0009](../03-pattern-analysis/adr/0009-ai-provider-subscription-first.md) · FR-14 |
| 미확인 | **Anthropic 약관 확인**은 팀 밖 배포(베타) 전에 하기로 한 일로 아직 안 했다 — 질문이 오면 "배포 전에 확인할 일로 적어 두었다"고 답한다 |

### 카드 9 — Q13 "내 비밀번호 · 키가 AI로 나가지 않나요?"

| 칸 | 내용 |
|---|---|
| 결론 | **보내기 전에 비밀번호 · 키 모양을 찾아 멈추고 사용자에게 묻습니다.** 값은 화면에 다시 보이지 않습니다. |
| 이유 1 | 막지 않고 "그대로 진행 / 수정"을 고르게 해서 사용자가 결정합니다. |
| 이유 2 | 경고 문구는 무엇이 의심되는지만 말하고 값을 다시 보이지 않으며, 키는 환경변수에만 두고 레포 · 화면 · 기록에 남기지 않습니다. |
| 사례 | 화면에 노란 카드 "보내기 전에 잠깐!"이 뜹니다(`sensitive.js`). 먹이 주기 화면은 비밀번호처럼 보이는 구간을 **빼고** 보냅니다. |
| 결론(재확인) | 완전한 차단이 아니라, 사용자가 알고 고르게 하는 안전장치입니다. |
| 출처 | [security-records.md](../../.claude/rules/security-records.md) 6-3 · FR-15 · `03-backend/navigator/sensitive.js` |
| 미확인 | 어떤 패턴까지 잡는지(잡지 못하는 모양)는 `sensitive.js` 시험을 읽고 담당(이재엽)에게 확인 |

### 카드 10 — Q14 "Claude Code의 허락 · 거절 길이 안전한가요? 답이 없으면요?"

| 칸 | 내용 |
|---|---|
| 결론 | 사람 대신 허용하는 **자동 길을 두지 않았습니다.** 답이 없거나 서버가 꺼지면 허용되지 않은 채 도구 자신의 확인으로 넘어갑니다. |
| 이유 1 | 허용 · 거절은 화면에서 사용자가 누른 결정만 따르고, 그 요청과 짝이 맞을 때만 적용합니다. |
| 이유 2 | 삭제 · 강제 푸시 · 키 노출처럼 되돌리기 어려운 일은 한 번 더 묻습니다. |
| 사례 | 섬에 승인 카드(무엇을 · 바뀔 내용)가 뜨고 사용자가 허용 · 거절을 누릅니다(FR-17, `approve-hook.js`). |
| 결론(재확인) | 안전하다고 단정하지 않고, 기본값을 "허용 안 됨"으로 둔 설계입니다. |
| 출처 | security-records.md 6-3 마지막 줄 · FR-17 · [API.md](../../03-backend/navigator/API.md) 3-13~3-15 |

### 카드 11 — Q15 "토큰은 한 번에 얼마나 드나요?"

| 칸 | 내용 |
|---|---|
| 결론 | 판정 한 번은 **평균 약 8천 토큰**이었고(연습 예시 9개 실측), 미리 녹화한 답으로 재생하면 **0 토큰**입니다. |
| 이유 1 | 호출 종류마다 크기가 다르므로 "한 번에 얼마"는 어느 호출인지 같이 말해야 합니다. |
| 이유 2 | AI는 사용자가 누를 때만 부릅니다 — 누르기 전에는 0 토큰입니다. |
| 사례 | 점검에서 이번 합계 72,375토큰 · 한 번 평균 8,042토큰(PR #98). 시연 녹화 17개를 만들 때는 149,991토큰이 들었습니다. |
| 결론(재확인) | 비용은 사용자의 구독 한도나 키에서 나가고, 시연은 재생으로 0 토큰입니다. |

## 3. 사용자 · 협업 · 앞으로

### 카드 12 — Q18 "게이트의 '예 / 아니요'는 스스로 누르는 건데, 이해 안 했는데 '예'를 누르면요?"

| 칸 | 내용 |
|---|---|
| 결론 | 지금 구조는 **스스로 누르는 확인**이고, 이해 없이 "예"를 눌러도 막는 장치는 문서에서 찾지 못했습니다. 한계로 인정하고 보완을 설명합니다. |
| 이유 1 | 확인을 사람에게 두는 이유는 카드 6과 같습니다(학습의 주체는 사람). |
| 이유 2 | "아니요"로 가는 길을 쉽게 만들었습니다 — 헷갈린 곳 고르기 → 답 → 한 장 요약. |
| 사례 | 시연에서 "아니요"를 한 번 거쳐 한 장 요약으로 돌아오는 흐름을 보입니다. 설계상 "아니요"가 3번이면 사람에게 넘기는 Hold가 있습니다. |
| 결론(재확인) | 완벽한 이해 검증이 아니라, 이해를 **묻는 습관과 쉬운 되돌아가기**를 만든 것입니다. |
| 출처 | FR-4 · FR-5 · [화면 흐름](../04-pattern-implementation/screen-flow-wireframe.md) ⑤ ⑥ |
| 미확인 | 거짓 "예"를 막는 확인 질문이 따로 있는지 — 이재엽 확인 |

### 카드 13 — Q25 "역할이 팀장에게 몰려 보이는데 기여는 균형이었나요?"

| 칸 | 내용 |
|---|---|
| 결론 | **커밋 수는 일부 계정에 크게 쏠려 있습니다.** 그래서 팀원의 기여를 커밋 수만이 아니라 **산출물 · 이슈 · 리뷰 기록**으로 보이도록 역할을 나눴습니다. |
| 이유 1 | 역할이 문서 · 인터뷰 · 화면 · 검증처럼 나뉘어 있고, 담당자 이름으로 커밋하기로 했습니다. |
| 이유 2 | 평가의 균형 기준은 역할의 명확성과 기여이며, 증빙은 Git 로그 · Issue · 리뷰 기록입니다. |
| 사례 | `git shortlog -sn --no-merges` 기준(2026-10-24) 작성자 계정 중 하나가 100건이 넘고 나머지는 한 자릿수에서 두 자릿수입니다. Jira 이슈와 PR 리뷰 기록으로 보완합니다. |
| 결론(재확인) | 쏠림을 숨기지 않고, 어떤 기록으로 균형을 보여 줄지 정해 두었습니다. |
| 출처 | [schedule.md](schedule.md) 3-1 · `git shortlog -sn --no-merges`(발표 직전에 다시 뽑아 쓴다) |
| 미확인 | git 작성자 이름과 팀원의 대응(별칭이 여럿) — **두승현이 협업 증빙 담당이므로 11/5 이후 정확한 표를 뽑는다** |

### 카드 14 — Q26 "AI(Claude)를 개발에 얼마나 썼나요? 어디까지 사람이 했나요?"

| 칸 | 내용 |
|---|---|
| 결론 | **많이 썼고, 썼다는 사실을 파일마다 표시해 두었습니다.** 결정은 사람이 합니다. |
| 이유 1 | Claude가 쓴 부분에는 `claude-drafted: 날짜` 표시를 남기는 규칙이 있습니다. |
| 이유 2 | 선택과 확정은 담당자 몫이고, Claude는 후보 · 초안 · 리뷰를 맡습니다. |
| 사례 | 2026-10-24 `grep` 결과 `01-docs` · `02-frontend` · `03-backend` · `04-tests`의 문서 · 코드 283개 중 **228개**에 표시가 있습니다. ADR마다 "이재엽이 정할 것"에 결정 기록이 따로 있습니다. |
| 결론(재확인) | AI를 숨기지 않고 어디에 썼는지 보이게 했고, 결정의 책임은 사람에게 두었습니다. |
| 출처 | [review-mode.md](../../.claude/rules/review-mode.md) · 각 ADR "정할 것" · `grep -rl claude-drafted` |
| 주의 | 숫자는 발표 직전에 다시 센다. 표시가 있다고 전체를 Claude가 썼다는 뜻은 아니다(일부만 쓴 파일도 센다) |
