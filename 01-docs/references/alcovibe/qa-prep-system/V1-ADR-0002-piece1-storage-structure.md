# ADR-0002: 조각 1의 슬롯·카드 저장 구조를 "구조화 마크다운"으로 결정

> **출처: 이재엽의 개인 프로젝트 "Alcovibe" 워크스페이스의 `qa-prep-system` 파일.** 팀 기준이 아니라 **참고 자료**다. 팀에는 같은 이름의 스킬(`.claude/skills/qa-prep`)이 이미 있다. 발표 준비(11/9~11/11)에 쓸 수 있다.


- Status: Accepted
- Date: 2026-09-27

## Context

발표 준비 시스템(세션 파일 (개인 저장소 파일 — 이번에 가져오지 않음))의
Technical Architecture는 이미 "파일 + Claude Code 스킬 하이브리드"([ADR-0001](../../../03-pattern-analysis/adr/0001-storage-and-interface.md)
승계)로 확정되어 있다. 이 하이브리드 자체는 5대 아키텍처 스타일 중 어디에도 깔끔히 들어맞지 않는다는 점도
[02-architecture-styles.md](../../../03-pattern-analysis/02-architecture-styles.md)의 참고 사례로 이미 다뤄졌다.

조각 1에서 새로 결정할 것은 그 파일 계층 **안에서 슬롯과 카드를 어떻게 저장하는가**다. 2단계에서 확정된
아래 요구사항이 이 결정을 요구한다.

- FR13 (Event-driven, Must/Basic): 슬롯 정리가 끝나거나 카드가 완성되면 자동으로 로컬 파일에 저장한다.
- FR20 (Ubiquitous, Should/Basic): 슬롯이나 항목이 추가되어도 기존 기록이 깨지지 않는 형식으로 저장한다.
- FR15~FR17 (확장성): 6슬롯에 담기지 않는 내용에 추가 슬롯을 제안하고 사용자가 확인하면 이어서 진행한다.
- FR6 (사람이 소리 내어 카드를 읽음): 카드는 사람이 바로 읽을 수 있는 형태여야 한다.

## Decision

슬롯 값은 파일 앞부분에 목록(YAML) 형식으로 두고, 카드와 설명은 그 뒤에 마크다운 본문으로 쓰는
**구조화 마크다운**으로 정한다. 지금 이 세션 파일 자체가 제목, 상태 태그, 변경 기록을 이런 방식으로
써 온 것과 같은 성격이며, 새 형식을 발명하는 것이 아니라 이미 쓰던 관행을 슬롯·카드에도 적용하는 것이다.

## Considered Alternatives

1. **자유 서술 마크다운** (지금 세션 파일의 서술 문단 형태 그대로) — 기각. 사람이 읽기는 가장 쉽지만,
   슬롯이 늘어나면(FR20) 어떤 문단이 어느 슬롯인지 프로그램이나 사람이나 구분하기 어려워진다.
2. **구조화 데이터 파일(JSON 등) 별도 관리** — 기각(지금은). 프로그램 처리에는 가장 좋지만 사람이 바로
   못 읽고, 이 저장소가 지금까지 전부 마크다운 문서로 되어 있는 관행과 어긋난다. 나중에 여러 사용자를
   다루는 플랫폼(후속 ADR, 번호는 그때 정함)에서 재검토할 수 있다.
3. **구조화 마크다운 (채택)** — 목록 부분은 슬롯이 늘어도 줄만 추가하면 되고(FR20), 본문 카드는 그대로
   사람이 읽는다(FR6). ADR-0001이 이미 "파일 + 사람이 읽는 문서"를 전제로 하고 있어 그 위에 자연스럽게
   얹힌다.

## Consequences

**장점**
- FR20을 만족한다: 새 슬롯이 추가돼도 목록에 한 줄을 더하는 것이라 기존 슬롯의 값이 깨지지 않는다.
- 사람이 읽는 카드(FR6)와 프로그램이 참조할 수 있는 슬롯 값을 한 파일 안에서 함께 관리한다.
- 지금 세션 파일이 이미 이 형태(제목, 태그, 표)로 진화해 왔으므로 새 관행을 배우지 않아도 된다.

**단점 / 리스크**
- 목록 부분을 실제로 프로그램(스킬)이 읽어 쓰는 코드는 4~5단계에서 만들어야 하며, 지금은 형식만 정한
  것이다. 형식이 실제 사용에 맞는지는 4단계 Walking Skeleton에서 확인한다.
- 사람이 손으로 목록 형식을 잘못 쓰면(들여쓰기 오류 등) 프로그램이 슬롯 값을 못 읽을 수 있다. 4단계
  스모크 테스트에 이 경우를 넣는다.
- FR21~FR27(근거-질문 일치 확인)의 원문 발언과 확인 상태를 이 구조 어디에 둘지는 아직 정하지 않았다 —
  4단계에서 구체화한다.

## 다음 단계

4단계(패턴 구현)에서 Walking Skeleton으로 실제 슬롯 목록과 카드 하나를 이 구조로 만들어 보고, 사람이
읽기와 프로그램이 읽기(다음 세션에서 슬롯을 다시 채우기)가 둘 다 되는지 스모크 테스트한다.
