## 2026-09-24

작업 브랜치: `test` (`template` 브랜치는 배포용 템플릿이라 건드리지 않음)

### 발견: PRD를 확인하지 않고 2단계로 넘어갈 수 있었다

발표 준비 시스템 프로젝트(세션 파일 (개인 저장소 파일 — 이번에 가져오지 않음))를
Full 등급으로 진행하다가, 1단계 게이트를 "PRD 확장 안 함"으로 Go 처리하고 2단계(수집, 명세)까지
진행했다. 이후 사용자가 PRD 상세형 확장으로 결정을 바꿔 게이트를 Recycle로 되돌렸고, 이미 쓴
2단계 산출물이 "잠정" 상태가 됐다. 사용자는 이 프로세스를 다시 돌릴 때 PRD를 확인하지 않고 넘어가는
일이 없어야 한다고 요구했다.

원인(프로세스의 구멍 4개):
1. 게이트 로그 템플릿에 "PRD 결정" 칸이 없어서 결정 없이도 Go를 쓸 수 있었다.
2. 1단계 완료 기준의 "PRD 섹션을 채움"이 초안인지 확정인지 규정하지 않았다.
3. 앞 단계 결정이 바뀔 때 뒤 단계 산출물을 어떻게 다루는지 규칙이 없었다.
4. 스킬이 PRD를 "물어본다"까지만 하고, 답을 어디에 기록하는지·안 정해졌을 때 막는지가 없었다.

### 수정 진행 (1단계부터 하나씩)

| 순서 | 수정 | 상태 |
|---|---|---|
| 1 | gates.md: 게이트 로그에 "PRD 결정" 칸 추가, 1단계 완료 기준에 "확정" 정의 추가 (구멍 1, 2) | 완료 |
| 3 | SKILL.md 명령 1 (1단계 절차): PRD 확장 여부를 단독 질문(3-1)으로, 답을 게이트 로그에 기록, 2단계 진입 조건 추가 (구멍 4) | 완료 |
| 2 | gates.md: "앞 단계 결정이 바뀔 때" 절 추가 — Go 철회, 재심사 행, 잠정 표시, 트래커 갱신, 재통과 전 정합성 확인 (구멍 3). 순서를 "1단계부터" 원칙에 맞춰 3번 뒤로 옮김 | 완료 |
| 4 | 다시 돌려 보기: 수정된 규칙으로 이 프로젝트의 1단계를 재검토 | 완료. 새 규칙으로 1단계를 다시 통과했다(게이트 로그 참고). 결과와 발견은 [test-log.md](test-log.md) |

수정 3에서 실패 원인 하나를 절차에 직접 넣었다: 사용자가 앞서 밝힌 선택("PRD로 확장")을 내가
추천으로 뒤집고, 여러 확인을 한 메시지에 묶어 "둘 다 맞아"를 확정으로 받아들인 것. 그래서
3-1에 "단독 질문", "포괄적 답은 확정 아님", "이미 밝힌 선택은 기본값" 규칙을 넣었다.

### 상태를 한 곳에서만 관리하도록 정리

같은 상태(게이트, PRD 확정 개수, 잠정 여부)가 README, test-log, worklog, 세션 파일에 따로 적혀 있어서
바뀔 때마다 수동으로 맞춰야 했고, 실제로 어긋났다. 예를 들어 worklog의 수정 진행표에 완료된 항목의
옛 "대기" 행이 남아 있었다. 사용자가 이런 중복을 없애고 진행사항을 다시 옮겨 적거나 보고하지 않아도
되게 하라고 요청해서, 상태의 원천을 아래로 정했다.

- 단계와 게이트: 세션 파일의 게이트 로그
- PRD 섹션 상태: 세션 파일의 PRD 각 섹션 태그(확정, 초안, 미정)
- 한눈에 보기: 트래커(게이트만 요약. 이 저장소 워크플로우가 정한 색인이라 유지)

README, test-log, worklog에는 개수나 상태 문장을 적지 않고 원천으로 링크한다. worklog에서 완료된 항목의
옛 "대기" 행을 지웠다.
