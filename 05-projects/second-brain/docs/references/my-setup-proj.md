- **무엇:** 사용자가 2026-09-02부터 만든 [gamercross/my-setup-proj](https://github.com/gamercross/my-setup-proj)
  ("대시보드 OS"). Electron + React 앱, Express 로컬 API, Python Claude 에이전트, 로컬 SQLite.
  우송대 2026-2학기 3개 강의의 공통 실습 환경이자 제출 산출물. 목표 완성 2026-11-30.
- **기준 시점:** `main` 0766dfe (2026-09-22, PR #85). 요약 원천은 그 저장소의 `docs/SYSTEM_ARCHIVE.md`.
- **이 문서의 역할:** 세컨드 브레인 각 단계에서 **다시 만들지 않고 가져다 비교할 재료**의 지도다.
  코드를 그대로 옮기라는 뜻이 아니다 — 세컨드 브레인은 마크다운 파일 저장으로 정했다(PRD 기술 구조).

## 1. 목적이 거의 같다 — 먼저 정해야 할 것

| | my-setup-proj (2026-09-14 사용자 진술) | 세컨드 브레인 (1단계 요약, 2026-10-01 확정) |
|---|---|---|
| 목적 | "진척도를 보는 것이 아닌, 자신의 프로젝트나 경험들이 모인 지식을 시각화하고 도식화해서 지식 가치를 올리는 것" | 쌓인 지식을 시각화하고 다시 돌려 쓰면서 스스로 발전하는 사이클 |
| 진행 관리 | 프로젝트 카드 + 기대정렬 체크인 + OKR + GitHub 커밋 | 프로젝트(과제 포함) 개발·진행 자동화, 놓친 일 막기 |
| 생활 | 일정·메일·Daily Brief (Gmail·Calendar·Notion) | AI 운영체제로 분리 |

**관계 — 사용자 결정 2026-10-01:** my-setup-proj는 사용자가 AI와 에이전트를 처음 써 본 **이 작업의 초안**이다.
"이 작업을 해보면서 한 작업의 노하우 … 이걸 가져올 부분만 가져오고 새롭게 만드는게 좋아보여서."
→ 세컨드 브레인은 **새로 만든다.** 아래 재료는 단계마다 "가져올지"를 사용자가 정하는 후보이고, 코드를 이어 쓰지 않는다.

## 2. 단계별로 가져올 재료

| 세컨드 브레인 단계 | my-setup-proj 재료 | 쓰는 곳 |
|---|---|---|
| 1→2 게이트 렌즈 공백 "기존 노트 앱과 무엇이 다른가" | REVERSE_PLAN §2-5: Notion·Sunsama·Akiflow·Linear는 *일*을 관리하고 이 프로젝트는 *일에서 나온 지식*을 관리한다. Notion은 페이지가 늘면 구조가 무너졌다(SYSTEM_ARCHIVE §2) | 청중 질문 답의 재료 |
| 1단계 태그 빈틈 | ADR-0029 자유 태그(다중) + `source ∈ {user, agent}`, 사용자 태그는 에이전트가 침범하지 않음 | 태그를 누가 붙이나 정할 때 |
| 2단계 요구사항·정량화 | `requirements/` FR·NFR·TRACEABILITY 구조, NFR-SEC 항목, 체크인 7질문(뭘·왜·언제까지·목표·전략·구체적으로·상태) | "놓친 일"의 마감(`until`)을 어디에 적을지, 보안 요구 문장 |
| 3단계 ADR 비교 후보 | 0015 로컬 우선, 0002·0009 SQLite(우리는 마크다운 — 왜 다른지 비교), 0024 OAuth 토큰 Fernet 암호화, 0031 안전 마크다운 렌더, 0035 기대정렬 체크인, 0036 지식 추세 뷰, 0037 레퍼런스 요약 추적 | 대안 비교 표의 한 줄 |
| 4~5단계 (Claude가 코드) | `/feature` 파이프라인: planner → developer → supervisor(PASS/CHANGES_NEEDED, 최대 2회) → finisher(검증·커밋). 사람 결정이 필요하면 `STOP_DECISION`으로 멈춤 | 우리 자체 검수 절차와 비교 |
| 보안 | `scripts/check-secrets.sh`(커밋 전 비밀값 검사) — 우리 기록·보안 기준이 "실제로 생기면 훅으로 승격"이라 적은 바로 그 장치 | 훅 승격 후보 |

## 3. 그 프로젝트가 남긴 교훈

- **가장 큰 교훈 — 사용자 진술 2026-10-01: "더 만들기엔 목적성을 잃어서 그만둔 케이스다."** 앱은 P0~P12까지
  만들어졌지만 목적이 흐려져 멈췄다. → 세컨드 브레인은 방향 점검(목적 → 방향 → 상태)을 계속 보고, 새 기능마다
  "목적 중 어디에 답하는가"를 먼저 묻는다.

아래는 그 저장소가 스스로 적은 약점(SYSTEM_ARCHIVE §8)이다.

- **D4: 자동 테스트는 통과했지만 실제 앱에서 눈으로 확인한 기록이 없다.** 수동 검증 백로그가 실행되지 않았다.
  → 세컨드 브레인 6단계 "놓친 일 수 실측"은 사람이 실제로 써 본 기록이 있어야 한다.
- **D3: 경계 규칙("에이전트는 읽기 전용" 등)을 코드 리뷰로만 지켰다.** → 우리 규칙도 반복되면 훅으로.
- **R-1: 1인 개발 + 시험 기간이 겹친다**(리스크 높음). → 세컨드 브레인 첫 버전 시기(렌즈 공백)와 맞대어 볼 것.

## 4. 보안 메모
