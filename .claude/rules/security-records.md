# 기록·보안 기준 (팀 레포 v1)

무언가를 **저장소에 기록할 때**, **밖으로 보낼 때**(AI 서비스, 외부 도구·MCP), **비밀값이나 다른 사람의 정보가 보일 때**,
PRD의 `Security & Compliance` 칸을 쓸 때 읽는다.

> **옮기지 않은 것.** V1의 3절·5절에는 개인 계정의 보안 설정, 개인 알림 서비스 연동, 개인 저장소 사실이 적혀 있었다. 한 사람의
> 보안 상태를 팀원 전원이 읽게 되는 것이라 옮기지 않았다. 팀에서 같은 사실이 필요하면 각자가 자기 것을 확인한다.

## 1. 전제

- 이 레포는 **비공개**이지만 **협업자 전원이 읽는다.** 나중에 공개로 바꾸면 이력째 보인다([migration.md](../../01-docs/00-overview/migration.md)).
- **Claude Code로 작업하는 모든 내용은 AI 서비스로 전송된다.** 무엇을 넣을지는 사람이 이 사실을 알고 정한다. 남의 원문을 내 세션에
  붙이면 그 글도 전송된다 — 공유본만 붙인다([team-sharing-security.md](../../01-docs/00-overview/team-sharing-security.md)).

## 4. 다른 사람의 정보 — 기본값

팀원의 이름, 메시지, 인터뷰 응답자의 말에는 다른 사람의 정보가 섞인다. 정해진 처리 방식이 없으므로 아래를 기본값으로 쓴다.

- **저장하지 않는다.** 대화 안에서 요약해 주는 것까지만 한다.
- 팀원은 이름·역할·하는 일 한 줄만 적는다. 커밋 내용·피드백 원문은 옮기지 않는다.
- 다른 사람의 정보가 든 그림·문서를 외부 도구(3절)로 보내지 않는다.
- 개인정보 관련 **법적 요구가 적용되는지는 Claude가 판단하지 않는다** — 확인이 필요하다고 표시한다.

## 5. 아직 정하지 않은 것 — 팀이 채울 칸

| 칸 | 왜 필요한가 | 언제 정하나 |
|---|---|---|
| 기록의 민감도 구분 (저장 가능 / 조심해서 저장 / 저장 금지) | 무엇을 어디까지 적을지 판단하는 기준. V1 세컨드 브레인은 세 단계로 정했다 | 공유 규칙 확정 때 — [team-sharing-security.md](../../01-docs/00-overview/team-sharing-security.md) |
| 인터뷰 기록의 보관 기간과 지우는 방법 | 쌓이기만 한다 | 인터뷰 설계 때 |
| 백업과 복구 | 저장소가 유일한 사본이 되면 잃을 위험 | 개인 데이터 저장 구조를 정할 때 |
| 서버가 생길 때의 인증·접근 권한 | 대회 시연은 서버 없이 한다. 서비스로 낼 때는 인증이 필요하다 | 서버를 올리기 전 — 6-3의 요청 판정 순서로 확인 |
| 라이선스·대회 후 소유 | 팀원 기여의 사용 범위 | **지금부터 팀원 합의** — 법적 판단은 Claude가 하지 않는다 |

채울 때는 공개 표준을 출처로 삼는다. 어떤 표준을 쓸지는 사람이 조사해서 고른다.

## 6. 자동화·검증·비밀값 — 사용자의 이전 작업에서 온 기준 (v1, 2026-10-01, 사용자 확정 "예 확정")

사용자 결정 2026-10-01: 참고 자료 8개에서 반복된 새 재료 중 **1 자동화 실패 처리 → 2 실제로 써 본 기록 → 5 비밀값·인증의
기계 확인** 순서로, "보안 사항이니 보안 기준과 사항들을 이 내용들을 토대로 준비"한다. 아래는 v0처럼 새로 지어낸 정책이
아니라 **사용자가 자기 저장소에서 이미 해 본 것**을 출처로 모은 것이다(각 줄 괄호). 숫자(재시도 횟수 등)는 비워 두고
세컨드 브레인 2단계 요구사항에서 정한다.

### 6-1. 자동화가 실패하면 숨기지 않는다 — 놓친 일을 막는 쪽의 보안 (가용성·무결성)

| 기준 | 출처 |
|---|---|
| 자동화(요약, 남은 날 알림, 동기화 등)가 실패하면 **사용자에게 알린다.** 조용히 멈추지 않는다 | No-Code 프로젝트 "실패 알림 설계" |
| 재시도는 **횟수 상한**을 두고, 간격을 늘려 가며 한다. 상한을 넘으면 멈추고 알린다 | my-setup-proj ADR-0016(1s/2s/4s, 최대 3회), K-Travel(1회 재시도) |
| 일부만 실패하면 결과는 만들되 **무엇이 빠졌는지 표시**한다 | K-Travel(맛집 검색 실패해도 경고 남기고 리포트), No-Code "대체 경로" |
| 자동화마다 **실행 기록**(언제, 무엇을, 성공/실패)을 남긴다. 기록에는 비밀값·다른 사람의 정보를 쓰지 않는다 | No-Code "실행 로그 비교", my-setup-proj 에이전트 활동 로그 |

### 6-2. 확인했다는 기록 — 누가 무엇으로 확인했는지 남긴다 (책임 추적)

| 기준 | 출처 |
|---|---|
| AI가 만든 결과물(코드, 요약, 문서)에는 **어떻게 확인했는지**를 함께 남긴다 — PR 자체 검수, `claude-drafted` 표시 | seoul-temperature-analysis "AI 사용 로그"(작업 / 이유 / 검증 방법) |
| "확인함"은 **실제로 실행·사용해 본 경우에만** 쓴다. 자동 테스트 통과와 사람이 써 본 것은 따로 적는다 | my-setup-proj D4(자동 테스트만 통과, 앱을 눈으로 본 기록 없음) |
| 증빙 이미지(스크린샷, 실행 화면)는 올리기 전에 **키·토큰·이메일·Webhook 주소·다른 사람의 정보가 없는지** 확인한다 | No-Code "스크린샷 관리" 점검표, seoul 실행 화면 캡처 |

### 6-3. 비밀값과 인증은 사람 기억이 아니라 기계로 확인한다

| 기준 | 출처 | 상태 |
|---|---|---|
| 커밋 전에 **비밀값을 검사**한다 — 금지 경로(`.env`, `*.pem` 등)와 추가된 줄의 키 패턴. 찾으면 값은 가려서 보여 준다 | my-setup-proj `scripts/check-secrets.sh` | [`.claude/hooks/check-secrets.sh`](../hooks/check-secrets.sh) — Claude의 `git commit`을 막고, 사용자의 터미널 커밋은 git pre-commit 훅으로 막는다(사용자 결정 2026-10-06). pre-commit은 로컬 설정이라 **새로 클론하면 다시 연결**: [`.claude/hooks/pre-commit.sample`](../hooks/pre-commit.sample)을 `.git/hooks/pre-commit`으로 복사하고 `chmod +x`. 저장소 최상위에 스크립트가 없으면(옛 브랜치, **`data` 브랜치 작업 폴더**) 주 작업 폴더의 것을 찾아 쓰고, 그래도 없으면 경고하고 건너뛴다(2026-10-06 worktree에서 커밋이 막힌 일, 2026-10-08 data 브랜치 ADR-0007로 고침). **Claude의 훅 모드는 세션 작업 폴더의 저장소만 본다** — 데이터 폴더에서 커밋하기 전에는 그 안에서 `check-secrets.sh --staged`를 직접 돌린다 (장부 W-12) |
| 서버·API·페이지를 **밖에 공개하기 전에 인증이 있는지** 확인한다 | data-ai-assistant(인증 없이 배포됨) | 체크리스트 6단계 항목 |
| 서버·API는 **요청을 인증 → 권한(역할) → 소유권 → 사업 조건(게이트) 순서로** 판정하고, 층마다 묻는 질문·코드 위치·거부 응답(401/403/404·409 등)을 표로 적는다. 세 판정을 한 조건문에 섞지 않는다. **거부 방식의 이유도 적는다:** 소유권 층은 자원의 존재를 흘리지 않으려 404, 권한(역할) 층은 존재는 보이되 막으므로 403이다 | Intent-Specify tasks.md "RBAC 설계 요약"(사용자 채택 2026-10-04; 404/403의 이유는 같은 절, 2026-10-08 보강 — 사용자 승인) | 3단계 보안 점검 항목 |
| 사용자 입력을 받아 저장·전송하는 기능은 입력에 **키·비밀번호·주민번호 같은 패턴이 보이면 경고한다 — 막지는 않고** "그대로 진행 / 수정"을 고르게 한다. 경고 문구는 무엇이 의심되는지만 말하고 값을 다시 보이지 않는다 | Intent-Specify SD_02 S1 민감정보 경고·SD_04 C9 (사용자 채택 2026-10-04) | 세컨드 브레인 "넣기" 기능의 요구 후보 (2단계 S 요구) |
| `main`에서 코드를 직접 고치려 하면 확인을 요청한다 | my-setup-proj `hook-code-branch-guard.sh` | 워크스페이스 훅 후보 |

### 6-4. 공개 표준 — **OWASP Top 10 + OWASP ASVS 둘 다** (사용자 결정 2026-10-01 "다")

큰 틀("무엇을 조심하나")은 **Top 10**으로, 확인 항목("무엇을 확인하나")은 **ASVS**로 잡는다. 2단계 보안 요구 문장은
Top 10 항목 이름으로 묶고, 6단계 보안 점검에서 ASVS의 해당 장을 확인 목록으로 쓴다. 장 번호·항목은 쓸 때 원문을
열어 확인한다(버전이 바뀐다 — 추측해서 옮기지 않는다).

| 후보 | 닿는 곳 |
|---|---|
| [OWASP Top 10 (2025)](https://top10.owasp.org/2025/) — A07 Authentication Failures, A09 Security Logging and Alerting Failures, A10 Mishandling of Exceptional Conditions (2026-10-06 원문 확인: 최신판이 2021에서 2025로 바뀜) | 6-3 인증 확인, 6-1 실행 기록·실패 처리 |
| [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) — 인증, 오류 처리·로깅, 비밀값 관리 장 | 6-1·6-3을 검증 가능한 항목으로 쪼갤 때 |
| 정보보안 3요소(기밀성·무결성·가용성) | 6-1이 왜 보안인가 — 가용성(자동화가 멈추지 않음)과 무결성(빠진 것을 표시) |

## 언제 이 기준을 꺼내는가 — 게이트마다

단계마다 무엇을 확인할지는 [`01-docs/catalog/checklist.md`](../../01-docs/catalog/checklist.md)의
"단계별 보안 점검 체크리스트"에 있고, 모든 게이트 리뷰에서 대조한다
([gates.md](../../01-docs/00-overview/gates.md) "보안 점검", 사용자 결정 2026-10-01). 5절의 빈칸도 이
체크리스트가 가리키는 단계에서 채워진다.

## 이 기준이 하지 않는 것

- 1~5절과 6-1·6-2는 읽고 따르는 기준이다. **6-3의 비밀값 검사는 훅으로 만들기로 사용자가 정했고**(2026-10-01), 2026-10-06에 `check-secrets.sh`로 만들었다 —
  사고가 생기기 전에 승격한 첫 사례다(v0에서는 "사고가 생기면 승격"이었다).
- 보안 심사를 하지 않는다. 우리 기록을 어떻게 적고 무엇을 보내지 않을지만 다룬다.
