# 참고 자료 받기 — 많은 파일·스크린샷을 워크스페이스와 프로젝트의 재료로 바꾸는 절차

<!-- claude-drafted: 2026-10-04 — 사용자 요청("자료가 너무 많아서 매번 헷갈려, 네가 초안 써줘. 워크플레이스에 더 추가할 수 있는지. 프로젝트를 준비할때 더 많은 스킬 아니면 내용들을 넣어서 준비할 수 있게")으로 Claude가 썼다. 세컨드 브레인 CLAUDE.md "자료가 많을 때"의 ①~④를 루트로 옮기고 ⑤ 꺼내 쓰기를 더했다. 확정은 사용자가 한다. -->

다음 경우에만 읽으세요: 사용자가 파일·스크린샷·저장소 링크를 **참고 자료로** 줄 때, 후보 장부
([`01-docs/catalog/reference-candidates.md`](../../01-docs/catalog/reference-candidates.md))를 고칠 때,
새 프로젝트를 준비하며 재료를 꺼낼 때(`dev-workflow` 명령 1의 1-1). GitHub 링크 하나를 참고 자료로 넣는 형식은
[세컨드 브레인 CLAUDE.md](../../05-projects/second-brain/CLAUDE.md) "참고 자료 넣기"에 있다.

## 왜 헷갈렸나 — 이 절차가 막는 두 가지

1. **상태가 여러 곳에 흩어졌다.** 같은 후보가 references 문서, 묶음 README의 비교 칸, 프로젝트 README에
   따로 적혀 어디가 최신인지 알 수 없었다. → **상태는 두 곳에만 적는다.**

   | 무엇의 상태 | 유일한 자리 |
   |---|---|
   | 묶음을 어디까지 받았나 (받음 → 문서화 → 비교 → 반영) | 큰 묶음: `~/proj/coding_marathon_result/코딩마라톤 가이드/README.md` 받은 기록표 (저장소 밖 — 2026-10-06 사용자 결정으로 워크스페이스 `레프런스/`에서 옮김). 릴스·게시물처럼 한 장씩 오는 **짧은 자료**: `~/proj/references/짧은자료/README.md` 받은 기록표 (저장소 밖, 2026-10-12 사용자 결정 — 한 자료 한 파일, 링크의 추적 꼬리를 떼고, 목록·문장은 원칙만 옮긴다) |
   | 워크스페이스로 가는 후보를 어떻게 판정했나 (후보 → 채택/보류/버림 → 반영됨) | [후보 장부](../../01-docs/catalog/reference-candidates.md) |

   나머지 문서(묶음 README, `01-docs/references/*.md`)는 **근거와 상세**만 담고 상태를 적지 않는다 — 장부 ID로 가리킨다.
2. **목적지가 섞였다.** 한 자료에서 워크스페이스(방법론·규칙·스킬)로 갈 것과 특정 프로젝트로 갈 것이 같이 나온다.
   → ③ 비교에서 **목적지를 먼저 나눈다.**

## 흐름

| 단계 | 하는 일 | 결과물 | 누가 | 끝 조건 |
|---|---|---|---|---|
| ① 받기 | 한 묶음씩 받고, 보안·이용 조건을 확인한다 | 기록표 한 줄 | 사용자가 넣고 Claude가 적는다 | 기록표 "보안 확인" 칸이 찼다 |
| ② 문서화 | 원본의 글자만 옮긴다 | 기록표와 같은 폴더의 `<묶음>/<폴더>/README.md` | Claude 초안, 사용자 대조 | 사용자가 원본과 대조해 "확인" |
| ③ 비교 | 겹침/새로움을 나누고, 새로움의 목적지를 정한다 | 장부 행 또는 프로젝트 references 문서 | Claude 초안 | 새로움마다 목적지가 있다 |
| ④ 반영 | 판정받은 후보를 맞는 파일에 넣는다 | 규칙·체크리스트·DoD·템플릿·스킬 | 사용자 판정, 작성은 요청에 따라 | 장부 상태 "반영됨" + 반영한 파일 링크 |
| ⑤ 꺼내 쓰기 | 새 프로젝트를 준비할 때 단계별로 쓸 재료를 보여 준다 | 세션 파일 "준비 재료" | Claude가 보여 주고 사용자가 고른다 | 사용자가 골랐다(아무것도 안 골라도 됨) |

## ① 받기

- **한 번에 한 묶음.** 묶음은 폴더 하나 또는 저장소 하나다. 여러 묶음을 한꺼번에 받으면 기록표에 각각 한 줄씩 적고, 문서화는 한 묶음씩 한다.
- **한 묶음의 크기:** 상위 폴더 1개, 또는 파일 10개 이하. **스크린샷은 5장 이하**(사용자 결정 2026-10-06, 세컨드 브레인 Q9). 2026-10-04에 전체 화면 스크린샷을 5장 넘게 한 번에 열었더니 이미지가
  비어서 왔다 — 큰 묶음은 Claude가 몇 장씩 나눠 읽는다.
- 원본(스크린샷·PDF·pptx)은 git에 넣지 않는다(사용자 결정 2026-10-04 "(다)"). 2026-10-06부터 코딩마라톤 가이드는 정리한 README도
  원본과 함께 이 워크스페이스 밖 `~/proj/coding_marathon_result/코딩마라톤 가이드/`에 둔다(사용자 결정). **그 폴더의 `.md` 문서만 `gamercross/coding_marathon_result`(비공개) 저장소의 `docs/coding-marathon-guide` 브랜치에 커밋했고(2026-10-08), 스크린샷·PDF·pptx 원본은 그 저장소 `.gitignore`로 제외했다**(도메인이 가려지지 않은 원본, 복제·재사용 금지 표시가 있는 PDF). 새 묶음을 어디에 받을지는 받을 때 사용자에게 묻는다. 릴스·게시물 같은 짧은 자료는 묻지 않고 `~/proj/references/짧은자료/`에 받는다(2026-10-12).
- 받자마자 확인한다 ([기록·보안 기준](security-records.md) 4절·6-2):
  - 키·토큰·이메일·도메인·외부 주소 → 자리표시로 가린다. 가렸으면 기록표 "보안 확인"에 무엇을 가렸는지 적는다.
  - 다른 사람의 이름·메시지 → 옮기지 않는다. 팀 자료는 내 몫이 중심, 팀원은 이름·직책·한 줄.
  - 이용 조건("복제 시 상의" 등) → 원문 대신 **원칙만** 적는다.

## ② 문서화 — 글자만 옮긴다

- 해석·평가를 쓰지 않는다. 해석은 ③에서 한다 — 섞으면 나중에 무엇이 원문인지 모른다.
- **스크린샷에서 생기는 세 가지를 표시한다:**

  | 문제 | 표시 |
  |---|---|
  | 가려지거나 흐려서 추정해 읽은 줄 | 줄 끝에 `[추정]`, README 머리에 개수 |
  | 스크롤 사이에 빠졌을 수 있는 칸 | README 머리와 기록표 메모에 "빠짐 의심: <어디>" |
  | 화면에 없던 칸 | `—` (지어내지 않는다) |

- README 틀은 자료 모양에 맞춘다(어떤 틀을 쓸지는 받은 기록표 "정해야 할 것" 3번).

## ③ 비교 — 겹침/새로움, 그리고 목적지

- 비교 대상: 워크스페이스 기준([gates.md](../../01-docs/00-overview/gates.md),
  [checklist.md](../../01-docs/catalog/checklist.md), `01-docs/02~07`, `.claude/rules/**`, `.claude/skills/**`)과 관련 프로젝트의 결정.
- **겹침**은 "우리 쪽 근거"만 남긴다. 장부에 넣지 않는다 — 새로 만들 것이 없다.
- **새로움**은 목적지를 하나 고른다:

  | 목적지 | 어디에 적나 |
  |---|---|
  | 워크스페이스 (모든 프로젝트에 쓰일 방법·규칙·스킬) | 장부에 행 추가 (`W-NN`) |
  | 특정 프로젝트 | `05-projects/<슬러그>/docs/references/<묶음>.md` |
  | 둘 다 | 장부에 쓰고, 프로젝트 문서는 장부 ID로 가리킨다 |

- **같은 후보가 다른 자료에서 또 나오면** 새 행을 만들지 않고 장부 "출처" 칸에 더한다. 출처가 둘 이상이면 판정 우선순위를 올리는 신호다.

## ④ 반영 — 후보를 맞는 자리에 넣는다

- 판정(채택/보류/버림)은 사용자가 한다. 한 번에 **최대 5개**씩 묻는다([review-mode.md](review-mode.md) 질문하는 법 2).
- 채택한 후보는 모양에 따라 자리를 정한다:

  | 후보의 모양 | 넣을 곳 |
  |---|---|
  | 매번 지켜야 하고 기계로 확인할 수 있다 | 훅 `.claude/hooks/` |
  | 매번 지켜야 하는 작업 방식 | `.claude/rules/*.md` |
  | 단계를 넘어가는 조건 | [gates.md](../../01-docs/00-overview/gates.md) DoR/DoD |
  | 잊기 쉬운 확인 항목 | [checklist.md](../../01-docs/catalog/checklist.md) |
  | 문서의 틀(칸) | `01-docs/0X-*/` 템플릿 |
  | 반복되는 작업 절차 | 스킬 — [skill-authoring.md](skill-authoring.md), 외부 스킬이면 `dev-workflow` 명령 4 |
  | 한 프로젝트에만 | 그 프로젝트 `CLAUDE.md` |

- 기준 파일(`CLAUDE.md`, `.claude/**`)을 고치면 [consistency.md](consistency.md)의 지도를 따른다.
- 반영하면 장부 상태를 "반영됨"으로 바꾸고 반영한 파일을 링크한다. 공개 템플릿으로 보낼 메커니즘이면 "템플릿" 칸에 표시한다([git-workflow.md](git-workflow.md)).

## ⑤ 꺼내 쓰기 — 새 프로젝트를 준비할 때

`dev-workflow` 명령 1에서 등급을 정한 직후(1-1), Claude가 아래를 **단계별 표 하나로** 보여 준다. 단계마다 최대 3개.

1. **이미 반영된 것** — 장부 "반영됨" 중 이 프로젝트가 밟을 단계에 닿는 것. 규칙에 들어가 있어 자동으로 적용된다는 안내만 한다.
2. **출발점 자료** — 레프런스 묶음 ↔ 단계 대응표(받은 기록표)에서 그 단계의 묶음 README — 지금은 [`reference-library`](../skills/reference-library/SKILL.md) 스킬이 단계별로 꺼내 준다. 템플릿·프리셋을 처음부터 만들지 않기 위해서다.
3. **스킬** — `.claude/skills/`와 [external-tools.md](../../01-docs/catalog/external-tools.md) "채택" 중 이 프로젝트에 맞는 것. 필요한데 없으면 명령 4 후보로 적는다.
4. **시험해 볼 후보** — 장부 "보류" 중 이 프로젝트에서 써 보고 판정할 수 있는 것.

고르는 것은 사용자다. 고른 목록은 사용자가 세션 파일에 "준비 재료"로 적고, 7단계 회고에서 실제로 도움이 됐는지 본다 —
도움이 안 됐으면 장부 상태를 다시 판정한다.

## 이 절차가 하지 않는 것

- 판정하지 않는다. 장부의 "후보"는 Claude의 분류이고 채택은 사용자가 한다.
- 원본을 git에 넣지 않는다.
- 프로젝트 전용 재료를 장부에 넣지 않는다 — 장부가 다시 커져서 헷갈림이 돌아온다.
