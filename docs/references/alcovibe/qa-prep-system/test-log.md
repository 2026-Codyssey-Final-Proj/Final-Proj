## 테스트 1 — 발표 준비 시스템 (2026-09-24, `test` 브랜치)

- **대상:** 세션 파일 (개인 저장소 파일 — 이번에 가져오지 않음)
- **조건:** Full 등급, 프로젝트 트랙, 사용자 1명, 세션 1회
- **범위:** 1단계(문제 저장, PRD)와 2단계 일부(수집, EARS 명세 초안). 2단계 3~5번과 3단계 이후는 하지 않았다.
- **상태:** 진행 중. 현재 상태는 세션 파일의 게이트 로그와 PRD 태그가 원천이며 여기에는 적지 않는다.

### 관찰: 잘 작동한 것

- **인터뷰의 정성적 표현 → 숫자 되묻기:** "여유롭지만 핵심을 알릴 수 있게"가 나왔을 때 숫자 기준으로 되물었다.
- **등급 결정 트리:** Lite로 잘못 잡았을 때 "구현이 작은 것과 위험이 낮은 것은 다르다"는 판단의 근거가 됐다.
- **EARS:** 대화에서 나오지 않았던 예외(FR5 말하지 못한 경우, FR7 기준 초과)가 요구사항으로 드러났다.
- **게이트 재기록:** Go를 지우지 않고 "철회"로 남겨 되돌아간 이력을 추적할 수 있었다.

### 관찰: 뚫린 곳

**프로세스(문서)의 구멍 — 수정함**

| 2 | "PRD 섹션을 채움"이 초안인지 확정인지 규정 없음 | gates.md 1단계 완료 기준에 "확정" 정의 |

| 4 | 스킬이 PRD를 "물어본다"까지만 함 | SKILL.md 명령 1의 3-1 |

**Claude의 대화 행동 — 규칙으로 일부만 막힘**

- 1단계에서 설계 논의(조각 계획, 구조 후보)가 섞였다. 세션 파일에서 "1단계 밖에서 나온 후속 입력"으로 분리했지만 재발을 막는 규칙은 아직 없다.
- 사용자가 먼저 밝힌 선택("PRD로 확장")을 추천으로 뒤집었다. 3-1에 "이미 밝힌 선택은 기본값"으로 반영했다.
- 여러 확인을 한 메시지에 묶어 "둘 다 맞아"를 확정으로 받았다. 3-1에 "포괄적 답은 확정 아님"으로 반영했다.
- 승인받지 못한 제안(수작업 시연 우선)을 남긴 채 다음 단계로 넘어갔다. **이건 아직 규칙이 없다.**

### 미검증·한계

- 새 규칙으로 다시 돌리는 중이라 **수정이 실제로 작동하는지는 아직 확인되지 않았다.**
- 사용자 1명, 세션 1회라 재현성을 말할 수 없다.
- 스킬은 Skill 도구로 직접 호출했다. 자연어 트리거가 SKILL.md를 불러오는지는 확인하지 못했다.
- "템플릿 작성 5분 이내" Usability 목표는 재지 않았다. 1단계가 설계 논의와 섞여 길어져서 재도 의미가 약하다.
- 2단계 3~5번 이후 단계에 비슷한 구멍이 있는지 모른다.
- `main` 브랜치의 기존 검증 사례에 새 규칙이 부딪히는지 확인하지 않았다. Full 프로젝트 트랙에만 적용되도록 썼으므로 영향은 작다고 추정할 뿐이다.

## 테스트 2 — 6슬롯을 우리 프로젝트에 적용 (2026-09-26)

- **목적:** 조각 1의 가설("슬롯 구조가 준비하는 사람이 놓친 부분을 찾아낸다")을 우리 자신의 내용으로 미리 시험한다.
- **방법:** 이 프로젝트에서 사용자가 말한 내용만으로 6슬롯(상황, 목적, 이유, 전략, 요구, 기한)을 채우고(지어내지 않는다),
  비거나 얕은 슬롯에서 꼬리 질문(한 번에 최대 2개)을 만들어 답을 받는 것을 4라운드 반복했다.
- **조건:** 사용자 1명, 자기 프로젝트, 슬롯을 Claude가 채우고 "얕음"을 Claude가 판정했다.

### 라운드별 기록

| 라운드 | 꼬리 질문 | 사용자의 답 | 슬롯 변화 |
|---|---|---|---|
| 0 (기준선) | - | - | 상황 채워짐, 목적·이유 얕음, 전략 채워짐(근거 얕음), **요구·기한 비어 있음** |
| 1 | 요구(청중에게 기대), 기한 | 팀장, 투자자에게 목적을 그대로 전달 / 이 기능이 완성될 때까지 | 요구 채워짐(얕음), 기한 조건형(날짜 없음) |
| 2 | 기한(범위, 완성 조건), 요구(팀장·투자자가 판단하는 것) | 전체 시스템 구축과 발표까지 / 청중이 답변을 정확히 이해하고 넘어가면 부합 | 기한 범위가 시스템 전체로 확대, 요구에 판정 기준이 생김 |
| 3 | 목적(이해하고 넘어가면 곧 좋은 성과인가), 기한(범위, 날짜) | 10월 둘째 주까지 / 이 프로젝트의 이유는 심사 과정 | 기한에 날짜, 이유에 심사 맥락. **목적 질문에는 직접 답하지 않음** |
| 4 | 이유 확인, 기한과 범위 | 본인이 심사를 받는 자리 맞음 / 최소는 조각 1 시연 | 이유 확인, 최소 범위 확정, 일정과 범위 충돌 해소 |

### 관찰

- **빈 슬롯 탐지가 작동했다.** 대화 내내 나온 적 없던 기한과 요구가 슬롯 정리 직후 바로 드러났고, 4라운드 만에 둘 다 채워졌다.
- **새 정보가 나왔다:** 심사 맥락, 청중(팀장, 투자자), 날짜, 최소 범위, 요구 판정 기준. 이 중 심사 맥락은 목적을 "다른 사람에게 배포하는 제품"에서 "본인이 심사받는 발표"까지 넓혔다.
- **일정과 범위의 충돌은 기한 슬롯이 채워진 뒤에야 보였다.** 슬롯을 각각 채우는 것만으로는 부족하고, 슬롯끼리 대조하는 점검(예: 기한 × 범위)이 필요해 보인다.
- **사용자는 질문한 슬롯이 아니라 다른 슬롯의 정보로 답하기도 했다**(라운드 3). 답을 받아 어느 슬롯에 넣을지 매핑하는 단계가 필요하다.
- **조건형 답("완성될 때까지")은 날짜로 다시 물어야 나왔다.** 이 저장소의 "정성적 표현은 숫자로 되묻는다" 규칙이 슬롯 방식에도 필요하다. 반면 날짜를 못 줄 때는 "미정"으로 기록하는 규칙도 필요하다.
- **슬롯에 들어가지 않는 핵심 논의가 있었다.** 성공을 어떻게 재는가, 사후 합리화 위험, 범위 결정은 6슬롯 어디에도 자리가 없다.
- **핵심 맥락(심사)이 4라운드째에야 나왔다.** "왜"를 처음부터 더 깊이 물었다면 더 일찍 나왔을 수 있다.

### 한계

- 사용자 1명이 자기 프로젝트를 넣은 1회 시험이고, 채우기와 판정을 한 쪽(Claude)이 했다. **이것으로 슬롯 방식이 검증됐다고 말할 수 없다.**
- "얕음"의 판정 기준이 없어 판단이 주관적이다.
- 청중이 실제로 묻는 질문 데이터와 대조하지 않았다.

### 여기서 나온 설계 가설 (검증 전)

1. 답을 슬롯에 매핑하는 단계가 필요하다.
2. 슬롯 사이를 교차 점검하는 단계가 필요하다.
3. 조건형·정성적 답은 숫자나 날짜로 되묻고, 끝내 못 주면 "미정"으로 기록한다.
4. 6슬롯이 다루지 못하는 영역을 보완하는 장치가 필요하다(예: 마지막 메타 질문 "제가 안 물어봤지만 알아야 할 게 있나요?").

## 테스트 1 결과 — 수정한 게이트 규칙으로 1단계를 다시 통과함 (2026-09-26)

### 규칙이 실제로 작동한 곳

- **PRD 결정 칸과 "확정" 정의:** 확정은 사용자가 확인한 것만 인정했고, 그 덕분에 Claude가 사용자 확인 없이 붙인 "확정" 표시(Status)를 찾아 바로잡았다.
- **앞 단계 결정이 바뀔 때의 규칙:** 조각 1의 입력이 바뀌자 이미 확정했던 Feature Overview를 재확인 대상으로 되돌렸고, 다시 확정했다. 2단계 산출물은 "잠정"으로 남았다.
- **단독 질문:** 확인을 한 번에 하나씩 묻는 방식이 "둘 다 맞아" 같은 모호한 답을 막았다.

### 새로 발견한 것

| # | 발견 | 성격 |
|---|---|---|
| 1 | **1단계 완료 기준의 "정성적 표현 없음"이 2단계 3번(정량화)의 일과 겹친다.** 1단계에서 정성적 표현을 모두 없애려면 정량화를 미리 해야 하는데, 정량화는 2단계의 몫이다. 이번에는 남은 네 항목을 2단계 첫 과제로 넘기고 통과했다 | 워크플로우 문서의 긴장. gates.md와 1단계 README에서 정리가 필요하다 |
| 2 | **같은 상태를 여러 문서에 적으면 어긋난다.** README, test-log, worklog, 세션 파일에 개수가 따로 있었고 실제로 어긋났다. 상태는 세션 파일의 게이트 로그와 PRD 태그로만 두었다 | 규칙으로 아직 굳히지 않았다. template에 넣을지 결정이 필요하다 |
| 3 | **확정된 섹션을 나중 결정으로 고칠 때의 절차가 없다.** 이번에는 사용자 지시를 근거로 고치고 변경 기록에 남겼다 | 절차가 필요하다 |
| 4 | **PRD 확정에 많은 왕복이 들었다.** 섹션마다 확인을 받다 보니 이틀 동안 여러 번 오갔다. 일정이 짧은 프로젝트에는 무겁다 | 등급이나 확정 방식의 조정이 필요할 수 있다 |

### 한계

- 사용자 1명, 프로젝트 1개이고 1단계만 다시 돌려 봤다. **2단계 이후의 규칙은 아직 검증하지 못했다.**
- 이 결과는 my-dev-process의 `template`에 아직 반영하지 않았다.

## 테스트 3 — qa-prep 스킬 전체 흐름 손 실행 (2026-09-28)

5단계 완성 목표(FR1~FR14, FR21~FR27)를 시나리오별로 쪼개 확인 (개인 저장소 파일 — 이번에 가져오지 않음)한
뒤, 이번엔 **하나로 이어진 세션**으로 처음부터 끝까지 손 실행했다. 전문은
full-dry-run.md (개인 저장소 파일 — 이번에 가져오지 않음).

**방법:** 슬롯 값은 전부 이 프로젝트의 실제 확정 내용을 그대로 썼다(구성한 예시 없음).

**관찰:**
- 요구 슬롯을 3조건에 대조했더니 **실제로 0/3(얕음)이었다** — 지어낸 예시가 아니라 실제 PRD의 실제
  상태다. 이 프로젝트를 계속 다듬어 왔는데도 "청중에게 무엇을 바라는가"의 구체적 근거·사례는 아직
  없었다.
- 꼬리 질문 한 번으로 1/3까지 나아졌지만 여전히 "얕음" 기준(2개 이상)에는 못 미쳤다 — 한 번의
  되묻기로 항상 충분해지는 건 아니라는 것을 실제 데이터로 확인했다.
- 같은 세션에서 질문 두 개를 던졌더니 하나는 사례가 없어 미완성(FR5), 하나는 근거가 모두 있어 완성
  후 근거-질문 일치 확인(FR21~FR25)까지 통과했다 — 이 갈림이 정상 동작이다.

**한계:** 사람이 손으로 한 번 돌린 것이고, 자연어 트리거는 여전히 확인되지 않았다.

### 자연어 트리거 확인 시도 (2026-09-28) — 이 세션에서는 불가능

사용자가 `qa-prep` 자연어 트리거를 확인해 달라고 요청했으나, **이 세션에서는 확인할 수 없다.**
Claude Code는 세션 시작 시 사용 가능한 스킬 목록을 고정하는데, 이 세션은 my-dev-process
디렉터리에서 시작돼 `dev-workflow`만 로드됐다 — `qa-prep`은 그 뒤 qa-prep-system에 만들어져
이 세션의 목록에 없다. my-dev-process의 worklog에 이미 기록된 것과 같은 종류의 한계다
("자연어 트리거는 이 세션에서 테스트 불가 — 새 세션에서 직접 트리거해봐야 함").

**확인 방법(사용자가 직접):** qa-prep-system 디렉터리에서 새 Claude Code 세션을 열고, 스킬
이름을 지정하지 않은 채 "발표 준비해줘" 같은 요청을 해서 `qa-prep`이 실제로 반응하는지 본다.
