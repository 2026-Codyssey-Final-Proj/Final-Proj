## Context and Problem Statement

주력이 "게이트 판정 규칙"과 "장기 기억" 둘 다로 확정되었다. 그런데 판정(단계의 완료 기준을 충족했는가)을 **프롬프트에 맡길지, 코드 규칙으로 정할지**, 그리고 Claude를 부르는 곳을 **어디 한 군데로 모을지**가 정해지지 않았다. 이 둘은 API 계약(#7)과 수용·계약 테스트(#17·#19)의 모양을 정한다.

이미 정해진 규칙: 외부 AI 호출은 한 모듈에서만 한다([implementations.md](../../../.claude/rules/implementations.md) 6번, V1에서 가져옴).

## Considered Options

1. **판정을 전부 프롬프트에** — 단계 산출물을 Claude에게 주고 "충족했는가"를 묻는다.
2. **판정은 코드 규칙, Claude는 초안·리뷰·질문** — 완료 기준을 항목 목록으로 두고 코드가 충족 여부를 정한다. Claude는 초안을 쓰고, 리뷰 문장을 만들고, 모르는 곳을 묻는다.
3. **판정은 사람만** — 시스템은 체크리스트만 보인다.

## Decision Outcome (제안)

**Claude 제안: 2, 그리고 Claude 호출은 한 모듈(어댑터)로 모은다.**

| 이유 | 근거 |
|---|---|
| 같은 입력에 같은 판정이 나와야 시험할 수 있다 | #17 수용 테스트, #19 계약 테스트가 가능해진다 |
| "판정 규칙"이 주력이라면 그것이 눈에 보이는 규칙이어야 한다 | 기획 20점 — 프롬프트만으로는 "API를 그대로 쓴 것"으로 보일 수 있다 |
| 한 모듈이면 키·로그·실패 처리를 한곳에서 본다 | implementations.md 6번 |

## Consequences

- 완료 기준이 항목 목록으로 표현되어야 한다(항목 수는 11절 미정 값, 3단계에서 정함).
- 코드 규칙만으로 못 보는 판정(설계도의 질)은 Claude 리뷰로 보이되, **Go/Recycle은 사람이 정한다**(FR-3).
- 린트나 테스트로 "Claude 호출이 어댑터 밖에 없다"를 강제할 수 있다.
