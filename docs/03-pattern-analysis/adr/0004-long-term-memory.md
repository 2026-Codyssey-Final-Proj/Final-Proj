## Context and Problem Statement

장기 기억(역량·노력 기록, 결정, 배운 것)은 주력 두 가지 중 하나다. 어디에 어떤 모양으로 쌓고, **검색을 어디까지** 할지 정해야 한다. 기획안은 "문서 검색(RAG)"을 기술 구성으로 적었지만, 시연은 서버 없이 가상 데이터로 한다(FR-10).

이미 있는 것: V1의 지식 문서(`vault/지식/<목적>/`, 관찰·해석·행동 세 칸, 사용자·Claude 태그, 인용 횟수 — `knowledge.py`).

## Considered Options

1. **마크다운 문서 + 키워드·태그 검색** — V1 방식 그대로. 외부 서비스 없음.
2. **마크다운 문서 + 의미 검색(RAG)** — 문서를 임베딩해 검색한다. 임베딩 서비스나 모델이 필요하다.
3. **데이터베이스** — SQLite 같은 곳에 쌓는다.

## Decision Outcome (제안)

**Claude 제안: 1로 시작하고, 검색을 한 인터페이스 뒤에 두어 2로 바꿀 수 있게 한다.**

| 이유 | 근거 |
|---|---|
| 시연은 서버 없이 가상 데이터다 | FR-10 |
| V1에서 코드와 시험이 있다 | `knowledge.py`, `test_knowledge.py` |
| RAG는 임베딩 서비스·비용이 생기고, 일정(11/1)에 비해 크다 | 기획안 기술 구성, schedule.md |

## Consequences

- 1이면: 역량·노력 항목과 단위(11절 미정)가 문서 머리말·태그로 표현되어야 한다.
- RAG가 대회 평가에서 "기술"로 필요한지는 멘토링에서 확인할 일이다. 필요하면 2를 한 경로만 시연한다(ADR-0002와 같은 방식).
- 기억은 사람마다 따로 저장한다(ADR-0005).
